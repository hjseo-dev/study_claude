SOLID 원칙

객체지향 설계에서 "변경에 강한 구조"를 만들기 위한 5가지 원칙. 전부 결국 하나의 질문으로 귀결됨: "이 코드를 고쳐야 할 때, 얼마나 적은 범위만 건드리면 되는가?"

S단일 책임 원칙 (Single Responsibility Principle)

정의: 클래스(또는 모듈)는 단 하나의 책임만 가져야 한다. 더 정확히는 — "하나의 변경 이유"만 가져야 한다.

여기서 "책임"을 "기능 하나"로 오해하기 쉬운데, 정확한 기준은 "누구 때문에, 왜 바뀌는가"임.

먼저 오해 하나 짚기: "컨트롤러에 엔드포인트가 여러 개면 SRP 위반?"

아니다. UserController가 login, register, updateProfile, withdraw 같은 여러 엔드포인트를 갖는 건 — 전부 "유저 관리"라는 하나의 응집된 도메인 책임이라서 정상임. SRP는 "메서드가 몇 개냐"가 아니라 "변경 이유가 몇 개냐"를 보는 원칙.

OK — 여러 엔드포인트, 근데 하나의 책임(유저 관리)
@RestController
public class UserController {

    @PostMapping("/login")
    public ResponseEntity<?> login(...) { ... }

    @PostMapping("/register")
    public ResponseEntity<?> register(RegisterRequest request) {
        return userService.register(request);
    }

    @DeleteMapping("/withdraw")
    public ResponseEntity<?> withdraw(...) { ... }
}

진짜 위반 지점: register() 메서드 "안"

진짜 문제는 클래스 레벨이 아니라, register() 메서드 하나 안에 서로 상관없는 4가지 기술적 책임이 뭉쳐있다는 것:

  • 타팀 API 호출 로직
  • 우리 DB insert 로직
  • AD insert 로직
  • 메일 발송 로직

이 메서드는 네 가지 다른 이유로 바뀜: 타팀이 API 스펙을 바꾸면 바뀌고, DB 스키마가 바뀌면 바뀌고, AD 시스템이 바뀌면 바뀌고, 메일 서비스가 바뀌면 바뀜. 책임이 4개인 것 — "엔드포인트가 여러 개"인 것과는 완전히 다른 층위의 문제.

BAD — register() 메서드 "안"에 책임 4개
@Service
public class UserService {

    public void register(RegisterRequest request) {
        partnerApiClient.register(request);   // 1. 타팀 API 호출
        userRepository.save(request);         // 2. 우리 DB insert
        adRepository.insert(request);         // 3. AD insert
        smtpClient.sendMail(request);         // 4. 메일 발송
    }

    public void login(...) { ... }
    public void withdraw(...) { ... }
}

원칙 적용

UserController/UserService는 그대로 두고, register() 메서드 내부의 4가지 기술적 책임만 어댑터로 쪼갬. UserService.register()는 이제 오케스트레이터 역할만 하고, 각 책임은 별도 클래스에 위임됨.

GOOD — 책임별로 분리
@Component
public class PartnerApiAdapter {
    public void register(RegisterRequest request) { ... }
}

@Component
public class UserDbAdapter {
    public void insert(RegisterRequest request) { ... }
}
왜 중요한가: 책임이 섞여 있으면, 한 가지 이유로 수정할 때 다른 책임까지 같이 열어보게 되어 — 상관없는 로직까지 다시 테스트/리뷰해야 하고, 실수로 건드릴 위험이 생김. (이전에 다룬 레거시 가입 서비스의 문제와 동일한 원인.)

O개방-폐쇄 원칙 (Open-Closed Principle)

정의: 기능을 확장하는 데는 열려 있어야 하고, 기존 코드 수정에는 닫혀 있어야 한다.

이미 결제수단 추가 예시로 다룬 원칙. 핵심 요약:

상황기존 구조 (if-else)어댑터 패턴 적용
새 결제수단 추가기존 메서드를 열어서 분기 추가새 클래스 파일 하나 추가
기존 코드 영향있음 (다시 테스트 필요)없음 (건드리지 않음)
BAD — 추가할수록 분기가 쌓임
if (type.equals("CARD")) {
    cardPaymentApi.charge(amount);
} else if (type.equals("KAKAO")) {
    kakaoPayClient.pay(userId, amount);
} else if (type.equals("TOSS")) {   // 추가될 때마다 여기가 늘어남
    tossPayClient.pay(userId, amount);
}
GOOD — 새 파일만 추가, 기존 코드 無변경
@Component
public class TossPayAdapter implements PaymentAdapter {

    public void pay(String userId, long amount) {
        tossPayClient.pay(userId, amount);
    }
}
왜 중요한가: "확장"과 "수정"을 분리하면, 새 기능을 추가해도 기존에 잘 동작하던 코드가 깨질 위험이 사라짐.

L리스코프 치환 원칙 (Liskov Substitution Principle)

정의: 상위 타입(인터페이스/부모 클래스)을 쓰는 코드는, 그 자리에 어떤 하위 타입(구현체)을 넣어도 동일하게 동작해야 한다.

즉, "이 인터페이스의 구현체면 서로 바꿔 끼워도 안전하다"는 신뢰가 깨지면 안 됨.

위반 사례

PaymentAdapter 인터페이스의 pay(userId, amount)를 구현하는 어댑터가 3개 있다고 하자. 이 중 하나(예: CardPaymentAdapter)가 다음과 같이 동작한다면:

  • 다른 어댑터들은 amount가 0이어도 정상 처리하는데, 이것만 예외를 던짐
  • 다른 어댑터들은 실패 시 false를 리턴하는데, 이것만 런타임 예외를 던짐

→ 호출하는 쪽(오케스트레이터)이 "어떤 구현체가 들어올지 모른 채" 코드를 쓸 수 없게 됨. 결국 호출부에 "이게 카드결제면 예외처리 다르게"라는 분기가 다시 생김 — OCP가 깨지는 결과로 이어짐.

BAD — 이 구현체만 다르게 행동함
public class CardPaymentAdapter implements PaymentAdapter {

    public void pay(String userId, long amount) {
        if (amount == 0) {
            throw new IllegalArgumentException("0원 결제 불가");
            // 다른 어댑터(Kakao, Toss)는 0원이면 그냥 false 리턴하고 끝남
        }
        cardPaymentApi.charge(amount);
    }
}

원칙 적용

인터페이스가 약속한 동작 규약(contract)을 모든 구현체가 동일하게 지켜야 함: 같은 상황엔 같은 방식으로 반응(성공 시 리턴 형태, 실패 시 처리 방식 등)해야 함.

왜 중요한가: 어댑터 패턴, 전략 패턴처럼 "인터페이스로 구현체를 교체 가능하게 만드는" 모든 설계가 이 원칙 위에서 성립함. LSP가 깨지면 "교체 가능하다"는 전제 자체가 무너져서, 어댑터를 나눈 의미가 없어짐.

I인터페이스 분리 원칙 (Interface Segregation Principle)

정의: 클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다. — 즉, 거대한 인터페이스 하나보다 작고 역할이 명확한 인터페이스 여러 개가 낫다.

위반 사례

PaymentAdapter 인터페이스에 다음 메서드가 전부 들어있다면:

  • pay(userId, amount)
  • refund(paymentId)
  • cancelSubscription(userId)

그런데 카드결제는 구독 취소 기능이 없음. 그래도 인터페이스를 구현하려면 cancelSubscription()을 억지로 구현해야 함 (빈 메서드거나 예외를 던지는 식으로). 쓰지도 않을 메서드를 억지로 책임지게 됨.

BAD — 하나의 뚱뚱한 인터페이스
public interface PaymentAdapter {
    void pay(String userId, long amount);
    void refund(String paymentId);
    void cancelSubscription(String userId);   // 카드결제엔 불필요한 메서드
}

원칙 적용

인터페이스를 역할 단위로 쪼갬: PaymentAdapter(결제), RefundableAdapter(환불 가능한 것만), SubscriptionAdapter(구독 기능이 있는 것만). 필요한 것만 구현하면 됨.

GOOD — 역할별로 작게 분리
public interface PaymentAdapter {
    void pay(String userId, long amount);
}

public interface SubscriptionAdapter {
    void cancelSubscription(String userId);
}

// 카드결제 어댑터는 PaymentAdapter만 구현하면 됨
public class CardPaymentAdapter implements PaymentAdapter { ... }
왜 중요한가: 인터페이스가 비대해지면, 그 인터페이스를 구현하는 모든 클래스가 "안 쓰는 기능"까지 떠안게 되고, 인터페이스가 바뀔 때(메서드 추가 등) 관련 없는 구현체까지 전부 영향을 받음.

D의존 역전 원칙 (Dependency Inversion Principle)

정의: 상위 모듈(비즈니스 로직)은 하위 모듈(구체적인 구현)에 직접 의존하면 안 되고, 둘 다 추상화(인터페이스)에 의존해야 한다.

이미 실습한 내용과 정확히 같은 원칙임:

위반 (직접 의존)준수 (추상화에 의존)
OrderOrchestrator가 아는 것TossPayClient (구체 클래스)PaymentAdapter (인터페이스)
결제수단 교체 시Orchestrator 코드 수정 필요Orchestrator는 그대로, 어댑터만 교체
BAD — 구체 클래스에 직접 의존
@Service
public class OrderOrchestrator {
    private final TossPayClient tossPayClient;   // 토스 SDK를 직접 알고 있음
}
GOOD — 추상화(인터페이스)에 의존
@Service
public class OrderOrchestrator {

    private final PaymentAdapter paymentAdapter;   // 인터페이스만 알고 있음

    public OrderOrchestrator(PaymentAdapter paymentAdapter) {
        this.paymentAdapter = paymentAdapter;
    }
}

"역전(Inversion)"이라는 이름이 붙은 이유: 전통적으로는 상위 로직이 하위 구현을 직접 가져다 쓰는 방향인데, 이걸 "상위도 하위도 똑같이 인터페이스를 바라보는" 방향으로 뒤집기 때문.

왜 중요한가: Spring의 DI 컨테이너/Bean이 존재하는 이유가 사실 이 원칙을 실현하기 위한 도구임. @Autowired/생성자 주입으로 구체 클래스 대신 인터페이스를 주입받는 것 자체가 DIP를 지키는 행위.
