# review-response — 외부 코드리뷰 타당성 판단 및 대응 문서화

회사 리뷰어(사람 또는 AI)가 PR에 남긴 코드리뷰 코멘트를 하나하나 검토해서,
실제로 반영해야 하는지 판단하고, 그 판단 근거와 **구체적인 개선 코드**를
`.claude/docs/review-response/<브랜치명>.html`에 회차별로 누적 기록한다.

**기본은 판단+문서화이지만, 사용자가 문서의 특정 항목을 지목해서
반영을 요청하면 그 자리에서 실제로 코드를 고친다** (6번). 다만 이
스킬을 처음 부른 시점에 먼저 코드를 고치지는 않는다 — 항상 문서부터
만들고, 반영은 그 다음 사용자 요청에 따라 진행한다.

분류 기준(심각도별 세부 분류)과 HTML 문서 구조는
[references/classification-guide.md](references/classification-guide.md)와
[references/report-template.html](references/report-template.html)에
정리되어 있다 — 작성 전에 반드시 읽는다. 실제로 채워진 결과물 예시는
[examples/sample-report.html](examples/sample-report.html) 참고(사람이
결과물 형태를 미리 보기 위한 것이며, 스킬 동작에는 쓰이지 않는다).

## 0. 입력 파싱

1. 사용자가 대화에 붙여넣은 리뷰 코멘트 텍스트를 개별 코멘트 단위로
   나눈다. 각 코멘트에서 다음을 추출한다:
   - 위치 (파일 경로 + 줄 번호, 있으면)
   - 원본 코멘트 내용
   - 원본 심각도 라벨 (Critical/Major/Blocker 등 회사 리뷰어가 붙인 표기)
   - **리뷰어가 제안 코드를 함께 줬으면 그것도 별도로 보관한다** — 4-1
     단계에서 참고만 하고 그대로 베끼지는 않는다.
2. 심각도 라벨이 회사마다 다른 용어를 쓸 수 있다 —
   `references/classification-guide.md`의 매핑표를 참고해 Critical/
   Medium/Low 셋 중 하나로 정규화한다. 라벨 자체가 없거나 애매하면
   추측하지 않고 사용자에게 확인한다.
3. 위치 정보가 없는 코멘트(예: PR 전체에 대한 총평)는 별도로 표시해두고,
   특정 파일에 묶이지 않는 항목으로 처리한다.

## 1. 회차 판단

1. 현재 체크아웃된 브랜치명을 확인한다(`git branch --show-current`).
2. `.claude/docs/review-response/<브랜치명>.html`이 있는지 `Glob`으로
   확인한다.
   - **있으면**: `Read`해서 이전 회차들의 판단 이력을 파악한다. 이번
     코멘트 중 이전 회차에서 이미 다룬 것과 같은 지점/같은 취지를 다시
     지적하는 게 있으면(반박에 대한 재반박 등) 이전 판단과 연결지어
     처리한다. 이번은 (기존 최고 회차 + 1)차가 된다.
   - **없으면**: 이번이 1차이고, 새 파일을 만든다.

## 2. 프로젝트 컨텍스트 확보

1. `docs/STRUCTURE.md`가 있으면 `Read`해서 이 프로젝트의 설계 의도·
   컨벤션(네이밍, 계층 구조, 에러 처리 등)을 파악한다(Medium "틀림/
   의도됨" 판단과 4-1단계 개선 코드 작성 둘 다에 필요). 없어도 이 스킬
   때문에 project-struct를 강제로 돌리지는 않는다 — 어디까지나 판단에
   참고할 배경지식일 뿐이다.
2. **`.claude/` 아래 추가 참고 문서 확인**: 팀이 직접 넣어둔 프로젝트
   설명·규칙 문서가 있을 수 있다. `Glob`으로 `.claude/**/*.md`
   (`.claude/skills/`·`.claude/commands/`·`.claude/agents/` 같은 Claude
   Code 설정용 폴더는 제외)를 확인하고, 관련 있어 보이는 파일만
   `Read`한다.
3. `docs/analysis/`·`docs/5w1h/`에 이번 코멘트들과 관련 있어 보이는
   기존 분석 문서가 있으면 함께 참고한다 — 배경/의도 판단과 개선 코드
   방향에 도움이 된다.

## 3. 코멘트별 검토

각 코멘트에 대해:

1. **최신 코드 확인**: 리뷰가 가리킨 파일:줄을 `Read`해서 지금도 그
   문제가 실제로 남아있는지 확인한다 — 이미 다른 이유로 고쳐졌거나
   삭제된 코드면 "이미 해결됨"으로 표시하고 넘어간다.
2. **연관 코드 추적 (지적된 한 줄만 보지 않는다)**: 이 코멘트에 대응해서
   수정한다면 영향받을 호출부·연관 모듈까지 `Grep`으로 추적한다 —
   `code-review` 스킬의 호출부·사이드이펙트 추적과 같은 방법론이다. 그
   수정이 다른 곳에서 또 다른 문제를 만들 수 있는지까지 본다. **이 조사
   결과는 4-1단계 개선 코드 작성의 기반이 된다** — 여기서 확인 안 하면
   개선 코드가 사이드이펙트를 놓칠 수 있다.
3. **타당성 판단**: 1~2번 조사 결과와 프로젝트 컨벤션/설계 의도를
   근거로 이 리뷰가 실제로 맞는 지적인지 판단한다.
4. **분류**: `references/classification-guide.md`의 기준대로 심각도별로
   분류한다.

## 4. 분류 규칙 (요약 — 상세 기준은 references 참고)

- **Critical**: 무조건 "반영 필요"로 분류한다 — 여기서는 재반박하지
  않는다.
- **Medium**: 아래 3가지 중 하나로 분류한다.
  1. **반영해야 함** — 리뷰가 타당함
  2. **범위 밖/중요도 낮음** — 이번 작업과 무관하거나 연관은 있어도
     중요도가 낮음 → 반영 안 함 + 반박 근거 작성
  3. **확인 필요(틀림/의도됨 가능성)** — 리뷰가 틀렸거나 설계상 의도된
     것일 수 있음. **AI가 확신할 수 없는 영역이므로 절대 스스로 확정
     짓지 않는다** — "확인 필요"로 표시하고 사용자에게 최종 판단을
     맡긴다.
- **Low**: 아래 2가지 중 하나로 분류한다.
  1. **적용 추천** — 하면 좋음
  2. **적용 안 해도 무방**
  - Low도 Medium 3번처럼 "틀림/의도됨"에 해당하면 마찬가지로 확인
    필요로 표시한다.
- **반영 여부와 무관하게, 모든 항목에 판단 근거를 반드시 작성한다** —
  "반영 필요"든 "반영 안 함"이든 이유가 없으면 안 된다.

## 4-1. 개선 코드 작성 ("반영 필요" 계열 항목만)

Critical, Medium의 "반영해야 함", Low의 "적용 추천"으로 분류된 항목은
구체적인 **수정 코드(before/after 또는 diff 형태)**까지 문서에 담는다 —
말로만 된 개선 방향 설명에 그치지 않는다.

1. **리뷰어가 제안 코드를 함께 줬어도 그대로 베끼지 않는다.** 이
   프로젝트의 컨벤션(2단계에서 확보한 `docs/STRUCTURE.md`, `.claude/`
   문서, 기존 코드 스타일)에 맞게 다시 작성한다 — 리뷰어의 제안이 다른
   스택/스타일 기준일 수 있다.
2. 3단계에서 확인한 연관 코드(호출부 등)에 미치는 영향을 반드시
   반영한다 — **이 개선 코드를 그대로 적용해도 사이드이펙트가 없어야
   한다.** 호출부까지 같이 고쳐야 하면 그 부분도 함께 제시한다.
3. 아직 실제 파일에 적용하지 않는다 — 문서에 코드로만 담아둔다(5번).

## 5. HTML 문서 생성/갱신

1. `references/report-template.html`의 구조를 참고해서 실제 내용으로
   채운 완전한 HTML 문서를 작성한다(외부 CDN 없이 `<style>` 내부에 전부
   인라인 — `file://`로 열어도 그대로 보이게. 설명 텍스트는 표·배지와
   비슷한 크기로 작게 — 큰 본문 폰트로 붕 뜨지 않게 한다).
2. 기존 파일이 있으면(1번에서 확인) 전체를 다시 읽어서, 새 회차 섹션을
   추가하고 상단 요약 표도 전체 회차 기준으로 다시 계산해서 통째로
   다시 쓴다(HTML은 부분 추가가 안 되므로).
3. 반드시 포함할 내용:
   - **상단 요약 표**: 전체 코멘트를 회차·심각도·분류·**반영 상태**
     (반영 대기/반영 완료/반영 안 함/확인 필요) 기준으로 한눈에 보이게
   - **회차별 구분**: 1차/2차/3차를 구획으로 명확히 나눠서, 최신 회차가
     먼저 보이게
   - **각 코멘트 상세**: 원본 코멘트, 위치, 최신 코드 확인 결과, 연관
     코드 조사 결과, 분류, **반영/미반영 근거**, (반영 계열이면) 4-1의
     **개선 코드**(코드블록으로), 반영 상태
   - **확인 필요 항목은 시각적으로 눈에 띄게**(강조 색상) — 사용자가
     놓치지 않아야 한다
4. 저장 위치: `.claude/docs/review-response/<브랜치명>.html`. 폴더가
   없으면 만든다.
5. 대화창에는 전체 표를 다시 출력하지 않는다 — 핵심 요약(전체 개수,
   Critical 개수, 확인 필요 개수)과 **파일 정확한 경로**만 안내한다.

## 6. 반영 요청 처리

문서를 만든 뒤, 사용자가 "N번 반영해줘"/"이 항목 고쳐줘"처럼 특정
항목(들)을 지목하면:

1. **개선 코드 확보**: 지목된 항목에 4-1에서 미리 작성해둔 개선 코드가
   있으면 그걸 쓴다. **없으면**(원래 "확인 필요"나 "반영 안 함"으로
   분류됐던 항목을 사용자가 나중에 "그래도 반영해줘"라고 뒤집은 경우 등)
   지금 4-1과 같은 방식(프로젝트 컨벤션 반영, 연관 코드 고려)으로 개선
   코드를 새로 작성한 뒤 진행한다 — 코드 없이 넘어가지 않는다.
2. 실제 파일(들)에 적용한다. 개선 코드가 호출부 등 여러 파일에 걸쳐
   있으면 전부 적용한다. `backend-dev`와 동일한 원칙을 따른다 —
   프로젝트 컨벤션 준수, 왜 고쳤는지 주석 남기기.
3. 적용 후 컴파일/빌드로 확인한다.
4. HTML 문서를 다시 읽어서 해당 항목의 반영 상태를 "반영 완료"로
   갱신하고 다시 쓴다(요약 표 포함) — 원래 분류가 "반영 안 함"/"확인
   필요"였다면 그 사실과 "이후 반영으로 전환됨"을 함께 남긴다.
5. **"전체 다 반영해줘"처럼 여러 항목을 한 번에 요청받으면**: "반영
   필요" 계열 전체를 순서대로 위 1~4번을 반복한다. 대상이 5개 이상이면
   `backend-dev`와 동일하게 절반 정도 진행됐을 때 지금까지 반영한
   내용과 남은 항목을 공유하고 계속할지 확인한다.
6. **이번 회차에서 "반영 필요" 계열로 분류(또는 방금 전환)된 항목이
   전부 "반영 완료" 상태가 되면**, 바로 코드리뷰로 넘어가지 않고 먼저
   물어본다: "반영이 끝난 것 같습니다 — 수정된 버전에 대해 code-review를
   진행할까요?"
   - 사용자가 아직 남은 항목이 있다거나 다르게 답하면 그 지시를 따른다
     — 자동으로 넘겨짚지 않는다.

## 7. 반영 완료 후 코드리뷰

6-6번에서 사용자가 code-review를 승인하면:

1. `Skill` 도구로 `wlabs:code-review`를 호출한다(현재 브랜치 기준 —
   code-review가 작업트리 모드로 지금까지의 모든 변경을 리뷰한다).
2. code-review 결과에서 새로 발견된 사항이 있으면:
   - 어떤 원본 리뷰 코멘트를 반영하다가 생긴 문제인지 연결짓는다(가능한
     경우 — 무관한 발견이면 그렇다고 명시한다).
   - **이번 회차의 `<details class="round">` 섹션 안에** "이번 반영으로
     인한 추가 발견 사항" 하위 섹션을 추가해서, 새 발견 내용 + 관련
     원본 리뷰 항목 + 심각도를 기록한다 — 문서 전체 맨 밑에 두지 않는다
     (다음 회차에도 똑같은 반영→코드리뷰 흐름이 반복될 수 있으므로, 그
     회차 소속임을 명확히 한다). 채팅에만 보고하고 문서에 안 남기지
     않는다.
   - 새로 발견된 Critical/Medium/Low도 4단계 분류 규칙을 그대로
     적용한다. 단, 이 재귀 검토는 이번 회차 안에서 한 번만 반복한다 —
     또 새 코드를 고치고 또 리뷰를 도는 무한 루프로 만들지 않는다(추가
     반복이 필요해 보이면 사용자에게 다음 회차로 넘길지 물어본다).
3. 문제 없으면 이번 회차 섹션 안에 "code-review 결과 문제 없음"을 짧게
   기록한다.

## 8. 완료 보고

- 저장한 파일 경로.
- 이번 회차에서 "확인 필요"로 분류된 항목이 있으면 개수와 함께 강조해서
  알린다 — 조용히 넘어가지 않는다.
- "반영 필요" 계열 항목이 있으면, 문서에 개선 코드가 이미 담겨 있고
  "N번 반영해줘"처럼 지목하면 바로 적용할 수 있다고 안내한다.
- 반영을 진행해서 코드가 바뀌었다면, 이번 변경에 대한 테스트 코드가
  필요할 수 있다고 `/wlabs:test-case-creator`를 **언급만** 한다 —
  자동으로 이어서 실행하지 않는다.

## Anti-patterns

- Critical을 재검토한다며 반영 안 하는 쪽으로 판단하지 않는다 — 무조건
  반영 필요다.
- "확인 필요(틀림/의도됨 가능성)" 항목을 AI가 스스로 확정 짓지 않는다
  — 항상 사용자에게 넘긴다.
- 반영 안 하기로 한 항목에 근거 없이 넘어가지 않는다 — 반영/미반영
  모두 근거가 필수다.
- 리뷰가 가리킨 줄만 보고 판단하지 않는다 — 연관 코드(호출부 등)까지
  확인한다.
- **리뷰어가 제안한 코드를 프로젝트 컨벤션 확인 없이 그대로 베끼지
  않는다** — 이 프로젝트 스타일로 다시 작성한다.
- **개선 코드를 연관 코드(호출부 등) 고려 없이 작성하지 않는다** — 3
  단계 조사 결과를 반드시 반영해서, 적용해도 새 문제가 안 생기게 한다.
- 사용자가 지목하지 않았는데 먼저 나서서 코드를 고치지 않는다 — 문서
  작성까지가 기본이고, 반영은 항상 사용자 요청이 있어야 시작한다.
- "확인 필요"나 "반영 안 함" 항목을 사용자가 나중에 반영해달라고 했는데
  개선 코드가 없다고 그냥 넘어가지 않는다 — 그 자리에서 새로 작성한다.
- 반영 대상이 많은데(5개 이상) 중간 확인 없이 한 번에 다 고치고
  보고하지 않는다.
- 반영이 끝났다고 사용자 승인 없이 code-review를 바로 실행하지 않는다
  — 항상 먼저 물어본다.
- code-review에서 새로 발견된 문제를 채팅에만 보고하고 문서에 남기지
  않고 넘어가지 않는다.
- 기존 회차 문서를 무시하고 새로 덮어쓰지 않는다 — 이전 회차 이력은
  항상 유지·누적한다.
- HTML을 Artifact 도구로 올리지 않는다 — 항상 로컬 파일로만 저장한다.
