# review-response 사용법

회사 리뷰어(사람 또는 AI)가 PR에 남긴 코드리뷰 코멘트를 분석해서 타당성을
판단하고, 반영 여부·근거·**구체적인 개선 코드**를
`.claude/docs/review-response/<브랜치명>.html`에 회차별로 누적 기록하는
스킬입니다. 문서에는 실제 적용 가능한 코드가 담기고, 사용자가 특정
항목을 지목하면 그 자리에서 실제로 적용도 합니다. 별도 API 키나 외부
서비스 설정이 필요 없습니다.

> `code-review`(우리 스킬)와는 방향이 반대입니다. `code-review`는 git
> diff를 스스로 분석해서 리뷰를 **생성**하고, `review-response`는 이미
> **외부에서 받은** 리뷰 코멘트를 판단합니다. 다만 반영이 끝나면
> `review-response`가 직접 `code-review`를 이어서 호출합니다(아래 참고).

## 1. 호출 방법

자동으로는 실행되지 않습니다 (`disable-model-invocation: true`). 항상
명시적으로 불러야 합니다:

```
/wlabs:review-response
```

호출한 뒤, 회사 리뷰 도구에서 복사해온 리뷰 코멘트 텍스트를 그대로
붙여넣으면 됩니다. 형식(마크다운, 표, 그냥 줄글 등)은 자유롭습니다.

## 2. 사용 흐름

**1단계 — 판단 및 문서화 (항상 먼저)**

1. 입력 파싱: 코멘트별 위치·심각도·(있으면) 리뷰어의 제안 코드를
   추출합니다.
2. 회차 판단: 브랜치명 기준 기존 문서가 있으면 다음 회차로 이어갑니다.
3. 프로젝트 컨텍스트 확보: `docs/STRUCTURE.md`, `.claude/` 아래 문서,
   `docs/analysis/`·`docs/5w1h/`의 관련 분석까지 참고합니다.
4. 코멘트별 검토: 최신 코드 재확인 + 호출부 등 연관 코드 추적 + 타당성
   판단.
5. 분류: Critical(무조건 반영) / Medium(반영해야 함·범위 밖·확인 필요)
   / Low(적용 추천·적용 안 해도 무방). 반영·미반영 모두 근거 필수.
6. **개선 코드 작성**: "반영 필요" 계열 항목은 실제 수정 코드(before/
   after)까지 작성합니다. 리뷰어가 제안 코드를 줬어도 **이 프로젝트
   컨벤션에 맞게 다시 작성**하고, 연관 코드 조사 결과(호출부 등)를
   반영해서 부작용이 없게 만듭니다.
7. HTML 문서 생성/갱신 후, 파일 경로와 확인 필요 항목 개수를 안내합니다.

**2단계 — 반영 요청 (사용자가 지목했을 때만)**

문서를 보고 "N번 반영해줘"처럼 요청하면:

1. 지목된 항목에 개선 코드가 이미 있으면 그걸 쓰고, **없으면**(원래
   "확인 필요"나 "반영 안 함"이었는데 나중에 반영하기로 한 경우) 그
   자리에서 같은 방식으로 새로 작성합니다.
2. 실제 파일(들)에 적용합니다(`backend-dev`와 같은 원칙 — 컨벤션 준수,
   이유 주석). 호출부 등 여러 파일에 걸친 개선이면 전부 적용합니다.
3. 컴파일/빌드로 확인합니다.
4. 문서의 반영 상태를 "반영 완료"로 갱신합니다.
5. "전체 다 반영해줘"처럼 여러 개를 한 번에 요청하면 순서대로
   반복합니다 — 5개 이상이면 중간에 진행상황을 공유하고 계속할지
   확인합니다.
6. **이번 회차의 "반영 필요" 계열 항목이 전부 반영 완료되면**, 자동으로
   진행하지 않고 "code-review를 진행할까요?"라고 먼저 물어봅니다.

**3단계 — 반영 완료 후 code-review (사용자가 승인했을 때만)**

1. `/wlabs:code-review`를 현재 브랜치 기준(작업트리 모드)으로 호출합니다.
2. 새로 발견된 문제가 있으면, 어떤 원본 리뷰 항목을 반영하다가 생긴
   것인지 연결지어서 **이번 회차 섹션 안에** "이번 반영으로 인한 추가
   발견 사항"으로 남깁니다(문서 전체 맨 밑이 아니라 회차별로 —
   채팅에만 보고하지 않습니다). 문제 없으면 그렇게
   기록합니다.

## 3. 결과에서 주의할 점

- **Critical은 재판단하지 않습니다** — 항상 반영 필요로 분류됩니다.
- **"확인 필요"는 AI가 확정한 게 아닙니다** — 리뷰가 틀렸거나 설계
  의도가 있을 수 있다고 의심되지만, 최종 판단은 항상 사용자 몫입니다.
- **리뷰어가 준 제안 코드를 그대로 베끼지 않습니다** — 이 프로젝트
  컨벤션과 연관 코드 영향을 반영해서 다시 작성됩니다.
- 이 스킬은 사용자가 지목하기 전까지는 코드를 고치지 않습니다 — 먼저
  나서서 수정하지 않습니다.
- 반영이 끝났다고 code-review를 마음대로 실행하지 않습니다 — 항상
  먼저 승인을 구합니다.
- 이전 회차 문서는 덮어써지지 않고 항상 누적됩니다.
- 반영이 끝나면 테스트 코드가 필요할 수 있다고 `/wlabs:test-case-creator`를
  언급합니다 — 자동으로 실행하진 않습니다.

## 4. 자주 겪는 문제

- **개선 코드가 리뷰어 제안과 다르게 나옴**: 의도된 동작입니다 —
  프로젝트 컨벤션과 연관 코드를 고려해서 다시 작성하기 때문입니다.
  리뷰어 제안이 이미 적절하면 결과가 비슷하게 나올 수도 있습니다.
- **같은 지적을 리뷰어가 회차마다 반복함**: 이전 회차의 반박 근거를
  받아들이지 않고 계속 재지적하는 경우, "확인 필요"로 격상해서 사용자가
  직접 판단하도록 안내합니다.
- **반영 다 됐는데 code-review 질문이 안 나옴**: "반영 필요" 계열
  항목이 아직 다 안 끝났을 수 있습니다 — 요약 표에서 "반영 대기"가
  남아있는지 확인해보세요.
- **위치 정보가 없는 총평성 코멘트**: 특정 파일에 묶이지 않는 별도
  항목으로 처리됩니다.

## 5. 개선/확장 아이디어

- 아직 실전 사용 데이터가 없어서, Medium/Low 분류 기준과 개선 코드
  품질이 실제 회사 리뷰 성향에 맞는지는 여러 번 써보면서 다듬어질 수
  있습니다.
- 지금은 리뷰 코멘트를 대화에 직접 붙여넣는 방식만 지원합니다 — 필요해
  지면 `gh api`로 GitHub PR 리뷰를 직접 가져오는 방식을 추가할 수
  있습니다.
- 7번(반영 완료 후 code-review)에서 새 문제가 반복적으로 발견되는
  경우의 재귀 처리는 "이번 회차에서 한 번만 추가 반복" 정도로 단순하게
  잡아뒀습니다 — 실사용하면서 더 정교하게 다듬어질 수 있습니다.
