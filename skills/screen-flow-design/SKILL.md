# 🧭 화면 구조 설계

기능 요구사항과 데이터 모델을 바탕으로 사용자가 마주칠 화면들을 정의하고, 화면 간 이동 플로우를 설계하는 스킬.

**전제**: 데이터 스키마(db-schema-design)는 이미 확정되었고, 이를 토대로 사용자가 어떤 화면에서 어떤 데이터를 입력/조회하는지 설계하는 단계.

## 0. 입력물 확보

1. `docs/features/<기능명>/database.md` — 데이터 모델(엔티티/필드/관계)
2. 기능 목록 및 사용자 흐름 — "사용자가 이 기능을 사용하려면 어떤 순서로 화면을 거쳐야 하는가"

## 1. 화면 목록 도출

기능별로 필요한 화면들을 나열한다. 각 화면마다:
- **화면명**: 로그인, 회원가입, 개체 목록, 개체 상세, 급식 기록 입력, 등
- **용도**: "사용자가 뭘 하는 화면인가" (등록/조회/수정/삭제/확인)
- **주요 UI 요소**: 입력 필드, 버튼, 리스트, 등

사용자에게 확인받는다 — 임의로 화면을 추가/삭제하지 않는다.

## 2. 네비게이션 플로우

화면 간의 이동을 Mermaid `flowchart`로 시각화한다:
- 정상 흐름 (성공 경로)
- 오류 처리 (예: 형식 오류, 인증 실패 → 이전 화면 또는 다른 화면)
- 백버튼/취소 버튼 동작

## 3. 화면 상세 설계

각 화면마다:
- **입력**: 어떤 필드를 입력받는가 (텍스트, 선택지, 사진 등)
- **출력**: 어떤 데이터를 표시하는가
- **액션**: 버튼/링크 목록 및 각각의 결과
- **유효성 검증**: 입력 필드의 제약 조건 (필수/선택, 형식, 길이 등)

## 4. 정보 구조 (IA) — 메뉴/탭

로그인 후 사용자가 접근하는 주요 섹션/메뉴 구조:
- 홈 (대시보드/목록)
- 개체 관리
- 기록 (급식, 건강, 등)
- 설정
- 등

## 5. 검증 체크리스트

- [ ] 모든 엔티티 (데이터)가 어느 화면에서 입력/조회되는가 명확한가
- [ ] 화면 간 이동이 직관적이고 사용자 흐름을 방해하지 않는가
- [ ] 오류/예외 상황에 대한 처리(메시지, 흐름)이 정의되었는가
- [ ] 모바일/웹 플랫폼 차이가 있다면 명시되었는가 (앱만 가능한 액션 등)

## 6. 산출물

- `docs/features/<기능명>/screen-flow.md` — 화면 목록, 네비게이션 플로우(Mermaid), 화면 상세 테이블, IA 구조도
- (선택) Figma/Sketch 프로토타입 — 디자인 비용이 높으면 생략 가능

## 7. 다음 단계 안내

완료 시 API 설계(api-spec-design)로 이어갈 수 있음을 안내한다.

## 주의사항

- 화면을 스킬이 임의로 정의하지 않는다 — 기능 목록 → 후보 화면 제시 → 사용자 확인 → 확정
- 모바일/웹 차이가 크면 각각 따로 설계한다
- 플로우는 사용자 관점에서 그린다 (시스템 흐름이 아니라)
