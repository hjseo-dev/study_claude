# project-struct 사용법

낯선(또는 오래 다룬) 코드베이스를 분석해서 프로젝트 설명, 언어/프레임워크,
코딩 컨벤션, **API 카탈로그**(URI·기능·인증), **외부 시스템 연동 맵**(어떤
기능/메소드가 어떤 외부 시스템을 쓰는지), 아키텍처 맵, 시작용 CLAUDE.md를
만들어주는 스킬입니다. 별도 API 키나 외부 서비스 설정이 필요 없습니다.

## 1. 호출 방법

자동 트리거됩니다 — "이 프로젝트 구조 안내해줘", "API 정리해줘", "이
프로젝트 온보딩해줘", "이 프로젝트가 어떤 외부 시스템과 연동되는지
정리해줘" 같은 말을 하면 별도 명령 없이 실행됩니다.

명시적으로 부르고 싶으면:

```
/wlabs:project-struct
```

## 2. 사용 흐름

1. Glob/Grep으로 패키지 매니페스트, 프레임워크 설정, 진입점, API
   정의 소스(OpenAPI/라우트/컨트롤러), 외부 연동 시그널(.env 키 접두어,
   SDK import 등)을 정찰합니다.
2. 기술 스택/아키텍처를 표로 정리하고, 계층이 복잡하거나 외부 연동이
   얽혀 있으면 Mermaid 다이어그램도 추가합니다(단순한 구조면 생략).
3. API 카탈로그(공식 스펙이 있으면 그것을 1차 소스로 사용)와 외부 시스템
   연동 맵(기능/메소드 ↔ 외부 시스템, 동기/비동기, 인증 방식)을 표로
   만듭니다. DTO/VO/Domain 클래스가 있으면 그 카탈로그와 개념 차이 설명도
   API 카탈로그 문서 끝에 추가합니다. 재시도/fallback 정책처럼 코드로
   확인 안 되는 항목은 "확인되지 않음"으로 명시합니다.
4. 코드베이스를 스캔하며 실제로 확인한 문제점(보안 노출, 아키텍처
   비일관성 등)을 심각도순으로 최대 10개까지 정리합니다. 억지로 채우지
   않습니다.
5. 산출물을 파일로 작성합니다: `docs/STRUCTURE.md`(구조 가이드, 표+
   다이어그램+문제점 Top 10), `docs/API.md`(API 카탈로그 + DTO/VO/Domain
   카탈로그), `docs/EXTERNAL-SYSTEMS.md`(외부 연동 맵), 그리고 프로젝트
   루트의 `CLAUDE.md`(100줄 이내, 기존 CLAUDE.md가 있으면 대체하지 않고
   보강, 위 세 문서로 링크). 각 파일 제목/섹션 제목에는 이모지를 하나씩
   붙입니다.
6. "API 목록만", "외부 연동만", "CLAUDE.md만"처럼 범위를 좁혀서 요청하면
   해당 Phase만 실행합니다 (SKILL.md의 예시 2~6 참고).

## 3. 결과에서 주의할 점

- API 카탈로그는 OpenAPI/Swagger 스펙이 있으면 그것을 1차 소스로
  사용합니다. 스펙과 코드가 다르면 스펙 쪽을 우선하되, 어긋남이 있으면
  알려줍니다.
- 외부 시스템 연동 맵은 실제 import/호출 코드 근거가 있는 것만
  기록합니다 — 내부 함수 호출까지 "연동"으로 부풀리지 않습니다.
- 컨벤션·인증 방식·재시도 정책처럼 코드에서 확신 있게 판단할 수 없는
  항목은 추측 대신 "확인되지 않음"으로 표시됩니다.
- 자격증명 평문 노출처럼 심각한 문제를 발견하면 문서에 적는 것과
  별개로 대화창에서도 바로 요약해 알립니다.
