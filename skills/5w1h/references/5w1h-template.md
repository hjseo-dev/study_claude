# 5W1H 분석 문서 템플릿 & 판단 기준

> 이미 있는 프로젝트/기능을 놓고 "추가 개발·유지보수·버그 수정·접근방법
> 결정·고려사항 검토"를 할 때 육하원칙 틀로 생각을 정리하는 용도다.
> `project-struct` 분석이 없는 프로젝트에서도, 이 스킬이 먼저
> `project-struct`를 실행해 배경지식을 만든 뒤 이어서 진행한다.

## 관점 (분석 시작 시 AskUserQuestion으로 제시)

- 추가 개발 (기존 기능 위에 새 기능을 얹는 경우)
- 유지보수 (기존 동작을 고치거나 개선하는 경우)
- 버그 수정 (기존 동작이 기대와 다르게 실패하는 경우 — 아래 전용 필드 사용)
- 접근방법 결정 (여러 구현 방식 중 하나를 고르는 경우)
- 고려사항 검토 (아직 방향을 정하기 전, 리스크/제약부터 짚어보는 경우)
- 기타 (직접 입력)

## 문서 템플릿

각 `##` 섹션 제목 앞 이모지는 아래 표에 고정된 값을 그대로 쓴다(문서마다
바뀌지 않게 하기 위함). 문서 최상위 제목(H1)의 이모지만 이번 주제에 맞게
매번 새로 고른다.

```markdown
# {제목 어울리는 이모지} {작업/요구사항 제목}

- 관점: {위 목록 중 선택}
- 우선순위: {긴급/높음/보통/낮음 — 파악 안 되면 "미정"}
- 작성일: {YYYY-MM-DD}

## 📋 요약

{5줄 이내. 무엇을·왜·어디에 영향·어떻게 할 것인지를 압축. 5W1H를 다 채운
뒤 맨 마지막에 작성하되, 문서 안에서는 맨 위에 배치한다}

## 👥 Who — 관련 시스템/이해관계자

- 대상 프로젝트(시스템): {이름}
- 영향받는 다른 시스템: {있음/없음 — project-struct의 외부 연동 맵을
  1차로 참고하고, 이번 작업과 직접 관련된 부분만 추려서 적는다}

## 🛠️ What — 무엇을

{관점(추가 개발/유지보수/버그 수정/접근방법 결정/고려사항 검토)에 맞춰
핵심 내용을 정리한다. 접근방법 결정이면 후보 방식들을 나열, 고려사항
검토면 짚어야 할 항목들을 나열한다}

### 범위 외 (Out of Scope)

{이번에 포함되지 않는 것을 명시한다. 딱히 없으면 섹션 생략. **관점이
"버그 수정"이면 이 섹션 대신 아래 버그 전용 필드를 쓴다**}

### 버그 전용 필드 (관점이 "버그 수정"일 때만)

- **재현 절차**: {버그를 재현하는 순서. 코드 조사로 확인한 실제 트리거
  조건을 구체적으로}
- **기대 결과 vs 실제 결과**: {정상이라면 어떻게 동작해야 하는지 / 실제로는
  어떻게 잘못 동작하는지}
- **환경 정보**: {재현에 영향을 주는 조건 — 브라우저/OS/데이터 상태/설정값
  등. 해당 없으면 "해당 없음"}
- **심각도**: {치명적/높음/보통/낮음 — 판단 근거를 한 줄로 함께}

## ⏰ When — 실행/적용 시점

{이 변경이 시스템 안에서 언제(어떤 트리거·시나리오에서) 적용/실행되는지.
project-struct 산출물(API 카탈로그 등)과 코드 조사로 채운다. "미정"으로
남기지 않는다}

### 일정 (있으면)

{요청 시점/희망 완료일 등 실제 일정 정보가 파악된 경우에만 쓴다. 파악 안
되면 이 하위 섹션 자체를 생략한다}

## 🗺️ Where — 어디에 영향이 있는지

### 프로젝트 내부

{영향받는 모듈/클래스/파일/API. `docs/STRUCTURE.md`·`docs/API.md`를 1차
소스로 삼고, 이번 작업과 직접 관련된 부분만 Read/Grep으로 재확인한다}

### 외부(다른 프로젝트/시스템)

{`docs/EXTERNAL-SYSTEMS.md`를 1차 소스로 삼는다. 이번 작업과 관련된 연동만
추려서 적고, 관련 연동이 전혀 없으면 "확인했으나 관련 연동 없음"이라고
쓴다}

## 💡 Why — 왜

{배경/목적. 사용자가 대화로 설명한 내용, 또는 Jira 등에서 받은 배경을
반영한다. 코드만 보고 배경을 지어내지 않는다}

## 🔧 How — 어떻게

{구현 접근 방식. 접근방법 결정 관점이면 후보별 장단점을 표로 비교하고
추천안을 짧게 제시한다}

## ⚠️ 고려사항 (Considerations)

{리스크, 제약, 트레이드오프, 놓치기 쉬운 엣지 케이스. "고려사항 검토"
관점일 때는 이 섹션이 문서의 핵심이 되므로 특히 꼼꼼히 채운다. 딱히 없으면
"특별한 고려사항 없음"이라고 명시한다 — 섹션 자체를 생략하지 않는다}

## 📊 다이어그램

{필요하면 Mermaid. 필요 없으면 이 섹션 자체를 생략}
```

## 다이어그램 포함 여부 판단

- **생략**: 단일 파일 로직 수정, 상수/설정값 변경, 단순 개선
- **포함**: 여러 클래스/모듈 간 상호작용 발생, 신규 API/엔드포인트 추가, DB 스키마 변경, 기존 플로우 변경

## 다이어그램 종류 선택

- **기본값** — 컴포넌트/서비스 간 호출과 순서가 함께 중요한 경우 (대부분) → `sequenceDiagram`
- DB 테이블 관계 자체가 신설/변경되는 경우만 → `erDiagram`
- 시스템 간 호출보다 사용자 조작 절차·조건 분기 자체가 핵심인 경우만 → `flowchart`
- 클래스/모듈의 내부 구조(필드·메서드·상속) 자체를 보여줘야 하는 경우만 → `classDiagram`

애매하면 시퀀스 다이어그램을 쓴다 — 한 문서에 여러 종류를 욱여넣지 않는다.
