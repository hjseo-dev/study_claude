# 🗂️ 데이터베이스 스키마 설계

요구사항을 바탕으로 엔티티를 식별하고, 테이블 구조·관계·제약조건을 설계해서 실제 실행 가능한 스키마로 산출하는 스킬.

**전제**: 뼈대(app-init)는 이미 있고, 실제 도메인 모델을 설계하는 단계. 여기서 나온 결과물이 다음 단계(화면구조, API 설계)의 기반이 된다.

## 0. 요구사항 확보

1. `docs/` 아래에 5W1H 분석, 기능 백로그, PRD 등 기존 요구사항 문서가 있는지 확인하고 읽는다.
2. 없거나 부족하면, 사용자에게 핵심 기능 목록(MVP 범위)을 먼저 확인한다 — 스키마는 "무엇을 저장해야 하는가"에서 나오므로, 기능이 불명확하면 먼저 정리해야 한다.

## 1. 용어 정의 (Terminology)

비즈니스 용어와 시스템 용어를 1:1로 매핑한다. (예: "캣맘" → `User`, "급식 기록" → `FeedingLog`) 이후 모든 산출물(엔티티명, 컬럼명, API, 화면)에서 이 용어를 일관되게 쓴다.

## 2. 엔티티 목록 도출

기능 목록에서 명사(주로 화면에 "관리/등록/조회"되는 대상)를 뽑아 엔티티 후보로 만든다. `AskUserQuestion` 또는 대화로 후보를 사용자에게 확인받는다 — 임의로 확정하지 않는다.

## 3. 엔티티 상세 설계

각 엔티티마다:

| 필드명 | 타입 | 제약조건 | 설명 |
|--------|------|----------|------|
| id | UUID | PK | |
| ... | ... | ... | ... |

- PK/FK, NOT NULL, UNIQUE, DEFAULT 값을 명시
- 필드명은 1번의 용어집과 일치시킨다

## 4. 관계 (ERD)

엔티티 간 관계(1:1, 1:N, N:M)를 Mermaid `erDiagram`으로 시각화해서 문서에 포함한다.

## 5. 검증 체크리스트

- [ ] 정규화: 같은 정보가 여러 테이블에 중복 저장되지 않는가
- [ ] 인덱스: 자주 조회/조인되는 FK·검색 컬럼에 인덱스가 있는가
- [ ] Soft delete 필요 여부: 삭제 대신 상태 플래그가 필요한 데이터가 있는가
- [ ] 타임스탬프: created_at/updated_at이 필요한 테이블에 빠짐없이 있는가
- [ ] 확장성: "기능을 계속 확장할 것"이라는 전제와 충돌하는 과도한 제약은 없는가

## 6. 산출물

- `docs/DATABASE.md` — 용어집, 엔티티 목록, 엔티티 상세 표, ERD(Mermaid), 검증 체크리스트 결과
- `backend/src/main/resources/db/schema.sql` — 실행 가능한 `CREATE TABLE` DDL
- (선택) 로컬 DB에 실제 적용 — 사용자에게 방법(psql/pgAdmin/DBeaver) 확인 후 진행. **DROP/ALTER 등 파괴적 SQL은 반드시 사용자 명시 확인 후에만 실행**

## 7. 다음 단계 안내

완료 시 다음 단계(화면구조 설계, API 설계)로 이어갈 수 있음을 안내한다.

## 주의사항

- 엔티티/필드를 스킬이 임의로 확정하지 않는다 — 후보 제시 → 사용자 확인 → 확정 순서를 지킨다.
- 스키마 변경(특히 기존 테이블 DROP/ALTER)은 되돌리기 어려우므로, 실행 전 항상 명시적 확인을 받는다.
