# 🧩 What to Build — 기능 범위 설계

프로젝트의 비전/타겟 사용자를 바탕으로 기능 후보를 도출하고, MVP 범위와 확장 로드맵을 사용자와 함께 확정하는 스킬.

**왜 스키마 설계보다 먼저인가**: 데이터베이스 스키마는 "무엇을 저장해야 하는가"에서 나온다. 어떤 기능이 있는지가 정해지지 않으면 스키마도, 화면구조도, API도 다 다시 손봐야 한다.

## 0. 배경 확인

1. `docs/` 아래에 5W1H 분석, PRD, 이전 대화에서 논의된 비전/타겟 사용자 정보가 있으면 읽는다.
2. 없거나 부족하면 사용자에게 짧게 확인한다: 누가 쓰는 서비스인지, 핵심 문제가 뭔지, 확장 방향이 있는지.

## 1. 기능 후보 브레인스토밍

1. 사용자가 이미 생각해둔 기능들을 먼저 듣는다.
2. **AI가 추가로 좋은 기능을 제안한다** — 사용자 설명(도메인, 타겟, 수익모델 등)을 바탕으로, 비슷한 서비스들의 일반적인 핵심 기능과 차별화 포인트가 될 만한 기능을 함께 제시한다. 단, 제안만 하고 채택 여부는 사용자가 정한다.
3. 후보들을 다음 기준으로 분류한다:
   - **MVP 후보**: 없으면 서비스가 성립하지 않는 핵심 기능
   - **확장 후보**: 있으면 좋지만 초기 출시에는 필수가 아닌 기능

## 2. MVP 범위 확정

`AskUserQuestion` 또는 대화로 MVP 후보 목록을 사용자에게 확인받아 최종 확정한다. 임의로 확정하지 않는다.

## 3. 확장 로드맵 정리

확장 후보들을 우선순위 순으로 정렬한다. 우선순위 판단 기준(예: 사용자 임팩트, 구현 난이도, 수익화 연관성)을 간단히 밝힌다.

## 4. 산출물

`docs/WHAT-TO-BUILD.md`에 다음을 정리한다:
- 프로젝트 한 줄 비전 (기존 문서 있으면 인용)
- MVP 기능 목록 (기능명 + 한 줄 설명)
- 확장 로드맵 (우선순위 순, 기능명 + 한 줄 설명 + 우선순위 근거)
- 범위 밖으로 정한 것(있다면) — 나중에 헷갈리지 않도록 명시

## 5. 다음 단계 안내

완료 후 `db-schema-design`으로 이어갈 수 있음을 안내한다 — 이제 확정된 기능 목록에서 엔티티를 뽑아낼 차례.

## 주의사항

- 기능을 스킬이 임의로 확정하지 않는다 — 제안은 적극적으로 하되, 채택/제외는 항상 사용자 확인을 거친다.
- MVP 범위를 과도하게 키우지 않도록 주의를 환기한다 (범위가 크면 뒤 단계 전부가 늦어짐).
