# 📄 README 작성

프로젝트 코드베이스를 분석해서 아래 6개 체크리스트 항목을 채운 README.md를 작성하는 스킬. 매 프로젝트마다 동일한 구조를 재사용한다.

## 체크리스트

| 구분 | 필요 내용 | 예시 |
|------|----------|------|
| 프로젝트 설명 | 프로젝트가 무엇을 해결하는지 2~3줄 | 주문 처리 시스템의 실시간 재고 동기화 모듈 |
| 기술 스택 | 사용 기술과 **선택 이유** | Java, Spring Boot, Kafka, Redis |
| 실행 방법 | 로컬 설치·실행 방법 | docker-compose up, ./gradlew bootRun |
| 주요 구현 | 본인이 구현한 핵심 기능 | 이벤트 처리, 중복 메시지 필터링 |
| 트러블슈팅 | 문제 상황과 해결 과정 | 메시지 중복 처리, 장애 재처리 |
| 데모/이미지 | 스크린샷, GIF, 배포 링크 | Grafana 대시보드 캡처 |

## 1. 프로젝트 스캔

README를 채우기 전에 실제 코드베이스에서 근거를 찾는다 — 추측으로 채우지 않는다.

- `package.json` / `build.gradle` / `pom.xml` / `requirements.txt` 등에서 기술 스택과 버전 확인
- 폴더 구조(Glob)로 프론트/백엔드/DB 구성 파악
- `docs/` 하위에 이미 설계 문서(스키마, API 명세, 화면 설계)가 있으면 "주요 구현" 섹션 근거로 활용
- git log / 최근 커밋으로 실제 구현된 기능 범위 확인 (계획만 있고 미구현인 것과 구분)

## 2. 각 섹션 작성 원칙

### 프로젝트 설명
"무엇을 해결하는가"에 집중한다. 기술 나열이 아니라 문제→해결 구조로 2~3줄.

### 기술 스택 — 선택 이유 필수
각 기술마다 "왜 이걸 골랐는지"를 한 줄로 덧붙인다. 이유를 알 수 없으면(사용자가 명시하지 않았고 코드에서도 근거가 없으면) 추측해서 쓰지 말고 사용자에게 물어본다. 일반적으로 근거가 될 수 있는 것들:
- 팀/개인의 기존 숙련도
- 생태계 크기, 레퍼런스 풍부함
- 프로젝트 요구사항과의 궁합 (예: 실시간성 → WebSocket/Kafka, 타입 안정성 → TypeScript)
- 기존 인프라와의 호환성

### 실행 방법
복사-붙여넣기로 바로 실행 가능한 명령어 블록. 환경변수가 필요하면 `.env.example`을 함께 안내.

### 주요 구현
"구현했다"고 말만 하지 않고, 구체적으로 무엇을(엔드포인트 개수, 핵심 로직 한 줄 설명) 구현했는지 적는다.

### 트러블슈팅
**처음 작성 시점에는 비워두거나 "아직 없음"으로 둔다.** 이 섹션은 실제 운영/개발 중 이슈가 발생했을 때 그때그때 다음 형식으로 추가한다:

```
**문제:** [증상]
**원인:** [근본 원인]
**해결:** [조치]
```

/readme-creator를 다시 호출하면 새 트러블슈팅 항목을 추가할 수 있는지 먼저 사용자에게 확인한다 — 기존 항목을 덮어쓰지 않는다.

### 데모/이미지
스크린샷 파일 경로나 배포 URL을 사용자에게 확인해서 링크. 없으면 섹션 자체를 생략하거나 "추가 예정"으로 표시.

## 3. 산출물

- 프로젝트 루트의 `README.md` (기존 파일이 있으면 구조를 유지하며 업데이트, 없으면 새로 생성)

## 4. 주의사항

- 코드에 없는 기능을 "구현됨"으로 적지 않는다 — 설계만 된 것과 실제 구현된 것을 구분
- 트러블슈팅은 사용자가 알려주기 전까지 지어내지 않는다
- 기술 선택 이유는 사용자 확인 없이 추측하지 않는다 — 애매하면 질문한다
