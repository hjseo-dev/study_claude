# test-case-creator 사용법

git 브랜치가 base 브랜치(master/main) 대비 만든 **모든 변경사항**을 분석해서,
기능·보안성·안정성·회귀 4가지 관점의 테스트케이스를 표로 도출하고, 프로젝트에
맞는 실제 테스트 코드(가능하면 Mock 포함)를 생성해주는 스킬입니다. API 키나
별도 사전 설정은 필요 없습니다 — 로컬 git 저장소와 프로젝트 코드만 있으면
됩니다.

## 1. 사전 준비

없습니다. 다만 정확도를 높이려면 미리 `/wlabs:project-struct`를 한 번
실행해서 `docs/STRUCTURE.md`를 만들어두면 좋습니다(없으면 이 스킬이 자동으로
먼저 실행합니다).

## 2. 호출 방법

```
/wlabs:test-case-creator <브랜치명>
```

- `<브랜치명>`을 생략하면 현재 체크아웃돼 있는 브랜치를 대상으로 합니다.
- base 브랜치는 `main`/`master` 중 존재하는 쪽을 자동으로 씁니다. 둘 다 없는
  저장소라면 어떤 브랜치와 비교할지 물어봅니다.
- "이 브랜치 테스트 코드 생성해줘", "TDD 작성해줘"처럼 자연어로 말해도 자동
  트리거됩니다(슬래시 명령이 필수는 아님).

예시:

```
/wlabs:test-case-creator feature/order-refund
```

→ `master`(또는 `main`) 대비 `feature/order-refund` 브랜치의 모든 커밋 누적
변경을 분석합니다.

## 3. 결과 예시

```
| ID | 관점 | 시나리오 | 입력/조건 | 기대 결과 | Mock 필요 | 비고 |
|----|------|---------|----------|----------|----------|------|
| F1 | 기능 | 정상 입력으로 환불 요청 생성 | 유효한 주문ID | 200 + 환불ID 반환 | - | |
| S1 | 보안 | 타 사용자 주문 환불 시도 | 다른 사용자 토큰 | 403 | 인증 서비스 mock | |
| ST1| 안정성 | 결제 API 타임아웃 | PaymentClient 지연 | 예외 전파 없이 실패 응답 | 결제 API mock | |
| R1 | 회귀 | 기존 환불 한도 로직 유지 | 변경 전과 동일 입력 | 변경 전과 동일 출력 | - | |

생성된 파일:
- src/test/java/com/example/order/RefundServiceTest.java (F1, S1, ST1, R1)

⚠️ 로컬 전용: 없음

📄 리포트: docs/test-reports/feature-order-refund_20260904-1530.html

지금 테스트를 실행할까요? (예/아니오)
```

"예"를 선택하면 감지된 빌드 도구(Maven/Gradle/npm/pytest 등)로 방금 만든
테스트 파일만 실행하고 결과를 보고합니다.

대화창에는 위처럼 요약만 나오고, 표 전체·발견된 이슈·실행 결과가 정리된
**로컬 HTML 리포트**가 `docs/test-reports/` 아래에 파일로 저장됩니다
(Claude Artifact로 올라가지 않는 순수 로컬 파일입니다 — 탐색기에서 더블클릭해
브라우저로 열어보면 됩니다). 실행 결과까지 반영해서 저장하므로, "예"를
선택해 테스트를 실행한 경우 리포트에 통과/실패 표도 함께 들어갑니다.

테스트케이스는 **최대 10개**까지만 표/코드로 만듭니다. 후보가 더 많으면
실제 버그 → 보안 → 안정성 → 회귀 → 기능 순으로 우선순위를 매겨 상위 10개만
남기고, "총 N개 중 상위 10개만 표시했습니다"라고 알려줍니다.

## 4. 자주 겪는 문제

- **"base 브랜치를 찾을 수 없습니다"**: `main`/`master` 둘 다 없는 저장소입니다
  (예: `develop`을 기본 브랜치로 씀). 물어보면 실제 base 브랜치명을 알려주세요.
- **테스트 프레임워크가 예상과 다르게 감지됨**: `docs/STRUCTURE.md`가 오래됐거나
  프로젝트에 여러 언어가 섞여 있을 수 있습니다. `/wlabs:project-struct`를 다시
  실행해 문서를 갱신한 뒤 재시도하세요.
- **일부 테스트에 "로컬 전용" 표시가 붙음**: 실제 DB/사설망/로컬 환경변수처럼
  Mock으로 대체할 수 없는 의존성이 있다는 뜻입니다. 억지로 Mock 처리하지 않고
  정직하게 표시한 것이므로, 해당 테스트는 로컬 환경에서 직접 실행해야 합니다.
- **diff가 너무 커서 분석이 오래 걸림**: 커밋 수가 많은 브랜치는 파일 목록을
  먼저 훑고 실제 로직 변경 파일만 골라 분석하지만, 그래도 변경 범위가 매우
  넓다면 특정 파일/디렉토리만 대상으로 좁혀 달라고 요청하면 더 빠릅니다.
- **테스트 실행 명령을 못 찾음**: 빌드 도구가 불확실할 때는 실행 전에
  정확한 명령을 물어봅니다. 알려주면 그 명령으로 실행합니다.

## 5. 개선 아이디어 (아직 구현 안 됨)

- 커버리지 도구(JaCoCo, Istanbul/nyc, coverage.py 등) 연동해서 diff 라인
  커버리지를 함께 보고하면 더 정량적으로 판단할 수 있습니다.
- 여러 브랜치를 한 번에 비교하거나, PR 단위(GitHub PR 번호)로 바로 대상 diff를
  잡는 옵션을 추가할 수 있습니다.
- 생성된 테스트가 실패했을 때 원인을 분석해 자동으로 1차 수정을 제안하는
  루프를 추가할 수 있습니다(현재는 실패 원인 요약까지만 함).
