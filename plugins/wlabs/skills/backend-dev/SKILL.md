# backend-dev — 5w1h 분석 기반 백엔드 구현

`5w1h` 스킬이 만든 분석 문서를 바탕으로, 그 계획대로 실제 백엔드 코드를
구현한다. **이 스킬은 항상 5w1h 분석 문서를 재료로 삼는다** — 대화
내용만으로 임의로 구현하지 않는다.

구현 시 확인할 체크리스트(트랜잭션 경계·입력검증·에러처리·인증인가·기존
코드 재사용 등)는 [references/implementation-checklist.md](references/implementation-checklist.md)에
정리되어 있다 — 구현 전에 반드시 읽는다.

> 프론트엔드 구현이 필요하면 이 스킬이 아니라 별도 프론트엔드 스킬을 쓴다
> (아직 없으면 사용자에게 필요 여부를 확인한다). 코드 리뷰(`/wlabs:code-review`)는
> 4번(자체 검증)에서 **항상 자동으로** 이어서 실행한다 — 별도로 부를
> 필요 없다. 테스트 케이스/코드 생성은 `/wlabs:test-case-creator`가
> 전담한다 — 이 스킬은 구현이 끝난 뒤 먼저 나서서 제안하지 않지만,
> 사용자가 테스트 실행을 요청하면 4번에서 필요할 때 그 스킬을 이어서
> 호출한다.

## 0. 원본 확인 (5w1h 분석 문서 필수)

1. 현재 프로젝트의 `docs/5w1h/` 폴더에서 이번 작업에 해당하는 분석 문서를
   찾는다 (가장 최근 수정 파일 우선, 여러 개면 어떤 건지 사용자에게
   물어본다).
2. **찾았으면**: 그 문서의 **관점 / Who / What / Where / How** (+버그
   수정이면 재현절차·기대결과)를 읽어 구현 계획의 재료로 삼는다.
3. **못 찾았으면(또는 이번 작업과 안 맞으면)**: 대화 내용만으로 바로
   구현하지 않는다. 대신 `AskUserQuestion`으로 "이번 작업에 대한 5w1h
   분석 문서가 아직 없는 것 같습니다. 지금 먼저 만들까요?"라고 물어본다.
   - **예**: `../5w1h/SKILL.md`(상대경로: `plugins/wlabs/skills/5w1h/SKILL.md`)를
     `Read`로 읽고 그 지침을 처음부터 따라 분석 문서를 먼저 만든다. 문서가
     만들어지면 그걸 원본으로 삼아 이어서 진행한다.
   - **아니오**: 사용자가 명시적으로 거부한 경우에만, 지금 대화에서 나온
     내용으로 최소한의 구현을 진행하되 "5w1h 분석 없이 진행된 임시
     구현입니다"라고 완료 보고 시 명시한다.

## 1. 프로젝트 컨벤션 확보

1. 현재 프로젝트 루트에 `docs/STRUCTURE.md`가 있는지 `Glob`으로 확인한다.
2. **있으면**: `docs/STRUCTURE.md`를 `Read`하고, 이번 작업과 관련 있어
   보이면 `docs/API.md`도 함께 `Read`한다. 특히 📝 컨벤션 표(네이밍/코드
   패턴/테스트/Git 컨벤션 + 이 프로젝트 특이 규칙)를 구현에 그대로
   적용한다.
3. **없으면**: 먼저 사용자에게 짧게 알린 뒤 `Skill` 도구로
   `wlabs:project-struct`를 실행해 산출물을 만들고 이어서 사용한다.
4. **언어/프레임워크 버전과 기존 의존성 확인 (항상)**: `docs/STRUCTURE.md`의
   기술 스택 표(버전 포함)를 1차로 참고하되, 실제 매니페스트 파일
   (`pom.xml`/`build.gradle`/`package.json` 등)을 직접 `Read`해서 정확한
   버전과 이미 추가된 라이브러리·플러그인을 재확인한다.
   - 이 버전에서 지원되지 않는 문법/API를 쓰지 않는다(예: 낮은 Java/Spring
     버전에서 최신 문법을 임의로 쓰지 않음).
   - 이미 있는 라이브러리·플러그인은 최우선으로 재사용한다 — 없는 걸
     있다고 가정하거나, 확인 없이 새 의존성을 추가하지 않는다(필요하면
     사용자에게 추가 여부를 먼저 확인한다).
5. **STRUCTURE.md만으로 부족하면 실제 파일을 확인한다**: 컨벤션 표는
   요약이라 이번에 작성할 코드의 세부 스타일(정확한 네이밍 규칙, 어노테이션
   사용법, import 순서, 특정 패턴의 구체적 문법 등)까지는 안 다룰 수 있다.
   부족하면 이번에 수정/생성할 파일과 같은 디렉토리 또는 같은 계층의 기존
   파일 1~2개를 `Read`해서 실제 코드 스타일을 직접 확인하고, 요약 문서보다
   **실제 코드를 우선**한다.
6. **STRUCTURE.md가 실제와 다르면 갱신을 제안한다**: 위 과정에서
   STRUCTURE.md 내용(컨벤션, 기술 스택 등)이 실제 코드와 다른 걸
   발견하면, 조용히 우회만 하지 말고 5번(완료 보고)에서 `project-struct`
   재실행을 제안한다.
7. **`.claude/` 아래 추가 참고 문서 확인**: 이 프로젝트의 5w1h/
   project-struct 산출물 외에도, 팀이 직접 넣어둔 설계·분석 문서가
   `.claude/` 폴더 아래 있을 수 있다. `Glob`으로 `.claude/**/*.md`
   (`.claude/skills/`·`.claude/commands/`·`.claude/agents/` 같은 Claude
   Code 설정용 폴더는 제외)를 확인하고, 이번 구현과 관련 있어 보이는
   파일만 `Read`해서 구현 계획에 반영한다. 없으면 그냥 넘어간다.

## 2. 구현 계획 확인

**조사가 먼저, 질문은 그다음이다** — 코드를 보면 풀리는 애매함까지
사용자에게 묻지 않도록, 아래 순서를 지킨다:

1. 0번 문서의 Where(영향받는 파일/모듈)와 How(구현 접근 방식)를 바탕으로,
   이번에 새로 만들거나 수정할 파일 목록을 먼저 정리한다.
2. 기존 프로젝트에 비슷한 기능이 이미 있으면(같은 계층의 유사 기능), 그
   코드 구조를 먼저 `Read`해서 실제로 따라 만들 패턴으로 삼는다 — 컨벤션
   문서만 보고 짐작하지 않는다. 이 조사로 로직 상세·예외 처리 방식 등의
   애매함이 풀리는 경우가 많다.
3. How 섹션에 여러 후보 방식이 비교돼 있었다면(접근방법 결정 관점), 그중
   추천안을 따르되 "이 방식으로 구현하겠습니다"라고 짧게 확인하고
   시작한다. 후보가 하나뿐이면 바로 진행한다.
4. **정보 충분성 확인(1~3번 조사 이후에도 남는 것만)**: 0번 문서 +
   1번 컨벤션 정보 + 2~3번 조사로도 메워지지 않는 부분이 있는지 확인한다.
   로직 상세, 예외 처리 방식, 파라미터 형식/기본값, 화면-API 연동 방식
   등 **애매하거나 명시 안 된 부분이 남아 있으면 절대 추측해서 진행하지
   않는다** — `AskUserQuestion`이나 대화로 반드시 먼저 확인하고, 답을
   받기 전에는 3번(코드 구현)으로 넘어가지 않는다.

## 3. 코드 구현

1. `references/implementation-checklist.md`를 따라 구현한다.
2. 1번에서 확보한 프로젝트 컨벤션(네이밍, 계층 구조, 매퍼/DAO 패턴 등)을
   그대로 따른다 — 이 스킬만의 새로운 스타일을 도입하지 않는다.
3. 범위 외(Out of Scope)로 명시된 부분은 건드리지 않는다.
4. 버그 수정이면 0번 문서의 재현 절차로 먼저 재현을 시도해보고(가능하면),
   수정 후 같은 절차로 해결됐는지 확인한다.
5. **기존 함수/메서드를 수정하는 경우, 그 코드만 보고 끝내지 않는다**:
   `references/implementation-checklist.md`의 8번(호출부 및 사이드이펙트
   확인)에 따라 `Grep`으로 호출부를 찾아 이번 변경이 호출부를 깨뜨리지
   않는지 확인한다. 호출부도 같이 고쳐야 하면 그 사실을 알리고 수정
   범위에 포함시킨다. (새로 만드는 코드에는 해당하지 않는다.)
6. **새로 작성/수정한 코드 위치마다 상세한 주석을 남긴다**: 무엇을
   했는지가 아니라 **왜 이렇게 구현했는지**(0번 문서의 Why/How와
   연결지어)를 적어서, 나중에 이 코드를 보는 사람이 배경을 알 수 있게
   한다. (일반적으로는 주석을 최소화하지만, 이 스킬의 산출물은 예외로
   상세 주석을 기본값으로 한다.)
7. **변경 규모가 크면(대략 파일 5개 이상 신규/수정) 중간에 한 번 멈춘다**:
   전부 끝낸 뒤 한꺼번에 보여주지 않고, 논리적 단위로 나눠 절반 정도
   진행됐을 때 지금까지 바뀐 파일과 남은 작업을 짧게 공유하고 계속
   진행할지 확인한다. 방향이 틀렸을 때 되돌릴 범위를 줄이기 위함이다.

## 4. 자체 검증

1. **컴파일/빌드 확인 (항상)**: 프로젝트의 빌드/컴파일 명령
   (`docs/STRUCTURE.md`의 빌드 도구 참고, 없으면 매니페스트 파일로 판단)으로
   에러가 없는지 확인한다. 도구를 특정할 수 없으면 사용자에게 확인 방법을
   물어본다 — 검증 없이 "됐다"고 넘어가지 않는다.
2. **컴파일/빌드 실패 시**: 원인이 명확한 단순 실수(오타, import 누락,
   타입 불일치, 세미콜론 등)면 스스로 고치고 다시 검증한다. 원인이
   불명확하거나 로직적 판단이 필요한 실패(설계가 잘못됐을 가능성 등)라면
   추측해서 고치지 않고 실패 내용 그대로 사용자에게 보고한다.
3. **코드 리뷰 및 반영 (항상, 컴파일 통과 후)**: `Skill` 도구로
   `wlabs:code-review`를 호출해 그 지침의 0~6단계(대상 확정 → 변경 범위
   확보 → 프로젝트 컨텍스트 → 호출부·사이드이펙트 확보 → 1차 발견 →
   2차 검증 및 심각도 분류 → 보고)를 그대로 따라, base 브랜치 대비 지금
   브랜치에서 만든 전체 변경사항(커밋 여부와 무관 — 현재 브랜치를
   대상으로 하면 code-review가 작업트리 기준으로 diff한다)을 리뷰한다.
   - **code-review의 7번(반영 여부 확인)은 따르지 않는다** — 대신 이
     스킬만의 정책을 따른다:
     - **Critical/Medium 발견**: 반영 여부를 다시 묻지 않고 그 자리에서
       바로 수정한다 — 실제 버그를 안은 채로 "완료"라고 보고하지 않기
       위함이다. 수정 후 1번(컴파일 확인)으로 돌아가 다시 검증한다.
     - **Low 발견**: 수정하지 않고 목록만 만들어 아래 5번(완료 보고)에
       함께 남긴다 — 사용자가 원하면 나중에 반영 여부를 고르게 한다.
   - 리뷰는 상세할수록 좋다 — 후보를 넓게 찾고 호출부까지 꼼꼼히
     검증한다. 발견 개수를 줄이려고 스스로 걸러내지 않는다.
4. **테스트 실행은 사용자가 명시적으로 요청했을 때만 진행한다** (자동으로
   먼저 돌리지 않는다). 요청받으면:
   1. 이번 변경에 대응하는 테스트 케이스 문서/코드(`test-case-creator`
      산출물 — `docs/test-reports/`의 관련 리포트, 또는 이미 생성된 테스트
      파일)가 있는지 확인한다.
   2. **있으면, 먼저 신선도를 확인한다**: 그 리포트/테스트 파일의 생성
      시각이 이번 세션에서 마지막으로 코드를 수정한 시점보다 **이전**이면
      (즉 3단계 구현이나 4-2단계 리뷰 반영으로 코드가 바뀐 뒤에 만들어진
      게 아니면) stale로 간주한다 — 오래된 리포트로 "테스트 통과"라고
      착각하지 않는다.
      - **최신이면** 그 문서/코드를 참고해서 관련 테스트를 실행한다.
      - **stale이면** 3번(재생성)으로 진행한다.
   3. **없거나 stale이면** `Skill` 도구로 `wlabs:test-case-creator`를
      실행해서 케이스와 테스트 코드를 새로 만들고(그 스킬의 지침을 그대로
      따름), 그 다음 이어서 테스트를 실행한다.
5. **의미 있는 테스트 인프라 자체가 없는 프로젝트라면** (예: 기본 컨텍스트
   로딩 테스트 하나뿐이거나 테스트 디렉토리가 사실상 비어있음) 컴파일
   확인만으로 충분하다고 안내하고 넘어간다 — 이걸 검증 실패로 취급하지
   않는다.

## 5. 완료 보고

- 새로 만들거나 수정한 파일 목록과 각 파일에서 한 일을 짧게 정리한다.
- **왜 이렇게 구현했는지 근거를 함께 설명한다**: 2단계에서 접근방법이
  여러 개였다면 왜 그 방식을 선택했는지(대안 대비 장단점)를 다시 요약
  하고, 기존 코드 패턴을 따랐다면 어느 코드를 참고했는지 밝힌다. 특별한
  판단 없이 단순 반복 작업이었다면 그 사실을 그대로 말한다 — 근거를
  지어내지 않는다.
- 4번에서 검증하지 못한 부분(로컬 전용 환경, 외부 연동 등)이 있으면
  명시한다.
- **4-3번(코드 리뷰)에서 반영한 Critical/Medium 항목**을 무엇을 왜
  고쳤는지와 함께 정리하고, **반영하지 않은 Low 항목**은 목록으로
  보여준 뒤 지금 반영할지 `AskUserQuestion`으로 물어본다.
- 이번 변경에 대한 테스트 코드가 필요하면 `/wlabs:test-case-creator`를
  쓸 수 있다고 **언급만** 한다 — 자동으로 이어서 실행하지 않는다(4번에서
  사용자가 테스트를 요청한 경우는 예외).
- **새 API 엔드포인트를 추가/변경했다면**, `docs/API.md`가 있는 경우
  그 문서도 함께 갱신할지 물어본다 — project-struct 산출물이 코드와
  어긋난 채로 방치되지 않도록 한다.
- **1번에서 STRUCTURE.md가 실제와 다른 걸 발견했다면**, `project-struct`
  재실행을 제안한다.

## Anti-patterns

- 5w1h 분석 문서 없이 대화 내용만으로 임의로 구현하지 않는다 — 없으면
  먼저 만들지 물어본다.
- **매니페스트 파일을 확인하지 않고 언어/프레임워크 버전을 짐작하지
  않는다** — `docs/STRUCTURE.md`가 오래됐을 수 있으므로 `pom.xml`/
  `build.gradle` 등으로 직접 재확인한다. 그 버전에서 안 되는 문법을
  쓰거나, 확인 없이 새 의존성을 추가하지 않는다.
- 완료 보고에서 "왜 이렇게 구현했는지" 근거를 생략하지 않는다 — 특히
  접근방법을 골라야 했던 경우 그 이유를 반드시 남긴다.
- **구현에 필요한 정보가 부족한데 추측해서 진행하지 않는다** — 로직
  상세·예외 처리·파라미터 형식 등이 애매하면 코드를 쓰기 전에 반드시
  먼저 물어본다.
- `docs/STRUCTURE.md`의 컨벤션 요약만 믿고, 실제 코드 스타일 확인 없이
  세부 문법을 짐작해서 쓰지 않는다 — 부족하면 실제 파일을 `Read`한다.
- 프로젝트 컨벤션을 무시하고 이 스킬만의 스타일(네이밍, 계층 구조 등)을
  새로 도입하지 않는다.
- 범위 외로 명시된 부분까지 손대지 않는다.
- **기존 함수/메서드를 수정하면서 호출부를 확인하지 않고 넘어가지
  않는다** — 그 함수 안에서는 맞아 보여도 호출부 가정이 깨질 수 있다.
- 코드를 작성/수정하고 왜 그렇게 했는지 주석을 남기지 않고 넘어가지
  않는다 — 이 스킬은 상세 주석이 기본값이다.
- 구현 후 검증(컴파일/테스트) 없이 완료라고 보고하지 않는다.
- **컴파일 확인 후 code-review 단계를 건너뛰고 바로 완료 보고로 가지
  않는다** — 이 스킬에서는 code-review가 선택이 아니라 자체 검증의
  일부다.
- Critical/Medium 발견을 반영만 하고 재컴파일 없이 끝내지 않는다 — 고친
  코드도 다시 검증한다.
- Low 발견을 완료 보고에서 누락하지 않는다 — 반영은 안 해도 목록은
  반드시 보여준다.
- 구현 직후에는 test-case-creator를 먼저 나서서 제안/실행하지 않는다 —
  존재를 언급만 한다. 단, 사용자가 테스트 실행을 **요청했는데** 케이스
  문서가 없으면 그때는 먼저 실행한다.
- **테스트 리포트/코드가 있다고 신선도 확인 없이 바로 재사용하지
  않는다** — 이번 세션에서 그 이후 코드가 바뀌었으면 stale이므로
  test-case-creator를 다시 실행한다.
- STRUCTURE.md가 실제와 다른 걸 발견하고도 완료 보고에서 갱신 제안을
  빠뜨리지 않는다.
- 컴파일/테스트 실패 원인이 불명확한데 임의로 고치지 않는다 — 원인
  불명확한 실패는 그대로 사용자에게 보고한다.
- 큰 변경(파일 5개 이상)을 중간 확인 없이 한 번에 다 끝내고 보고하지
  않는다.
- API를 추가/변경했는데 `docs/API.md` 갱신 여부를 묻지 않고 넘어가지
  않는다.
- 의미 있는 테스트가 없는 프로젝트에서 "테스트를 못 돌렸다"를 검증
  실패처럼 보고하지 않는다 — 컴파일 확인으로 충분하다고 명시한다.
