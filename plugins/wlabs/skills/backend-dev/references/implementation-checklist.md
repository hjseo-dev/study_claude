# 백엔드 구현 체크리스트

`backend-dev`가 코드를 실제로 작성/수정할 때 확인하는 항목. 프로젝트마다
스택이 다르므로 여기 항목은 언어/프레임워크에 무관한 **일반 원칙**이다 —
구체적인 문법/API는 `docs/STRUCTURE.md`와 기존 코드에서 확인한다.

## 1. 기존 코드 재사용 우선

- 비슷한 기능이 이미 있으면 그 구조를 그대로 따른다 — 같은 문제를 다르게
  푸는 새 패턴을 만들지 않는다.
- 공용 유틸/헬퍼가 이미 있으면 재사용한다. 없다고 확신하기 전에 먼저
  `Grep`으로 비슷한 이름의 기존 함수가 있는지 확인한다.

## 2. 트랜잭션 경계

- 하나의 비즈니스 작업이 여러 DB 쓰기로 이뤄지면, 트랜잭션 경계가
  프로젝트 관례(예: `@Transactional`, 명시적 커밋/롤백)에 맞게 걸려있는지
  확인한다.
- 트랜잭션 안에서 외부 API 호출처럼 느리거나 실패 가능한 작업을 하지
  않는다(락 시간 증가·롤백 범위 과다).

## 3. 입력 검증

- 외부에서 들어오는 입력(요청 파라미터/바디)은 null/빈 값/타입/범위를
  검증한다 — 프로젝트에 이미 쓰는 검증 방식(어노테이션 기반, 수동 체크
  등)을 따른다.
- 검증 실패 시 응답 형식이 기존 에러 응답 포맷과 일치하는지 확인한다.

## 4. 에러 처리 & 로깅

- 예외를 삼키지 않는다 — 처리하거나, 상위로 던지거나, 명시적으로 로깅한다.
- 사용자에게 내려가는 에러 메시지에 내부 구현 세부사항(스택트레이스, 쿼리
  등)이 노출되지 않는지 확인한다.
- 로그 레벨이 프로젝트 관례에 맞는지(정상 흐름을 error로 찍지 않는지 등).

## 5. 인증/인가

- 이 기능이 인증이 필요한지, 필요하다면 프로젝트의 인증/인가 체크가
  실제로 걸려있는지 확인한다(예: URL 프리픽스 기반 권한 규칙이 있는
  프로젝트라면 새 엔드포인트도 그 규칙을 따르는지).
- 다른 사용자의 리소스에 접근 가능한 경로(IDOR)가 새로 생기지 않는지
  점검한다.

## 6. 민감정보

- 비밀번호/토큰/개인정보를 로그나 응답에 평문으로 남기지 않는다.
- 새로 추가하는 설정값(API 키 등)을 코드에 하드코딩하지 않고, 기존
  프로젝트의 설정 관리 방식(환경변수, `.properties`/`.yml` 등)을 따른다.

## 7. 성능(가벼운 수준)

- 반복문 안에서 DB/외부 API를 호출하는 패턴(N+1)이 새로 생기지 않는지
  확인한다.
- 대량 데이터를 한 번에 메모리로 올리는 처리가 없는지 확인한다(있다면
  페이징/스트리밍 여부를 프로젝트 관례에 맞춰 검토).

## 8. 호출부 및 사이드이펙트 확인 (기존 코드를 고칠 때 필수)

- 새로 만드는 코드가 아니라 **기존 함수/메서드/클래스 멤버를 수정**하는
  경우, 그 코드만 보고 끝내지 않는다. `Grep`으로 프로젝트 전체에서
  호출부를 찾아서, 다음이 바뀌었다면 각 호출부가 그 변화에 맞게
  동작하는지 실제로 `Read`해서 확인한다:
  - 파라미터 개수/타입/순서, 반환 타입/의미(예: null 반환 → 예외로 변경)
  - 새로 발생하는 예외, 또는 더 이상 발생하지 않는 예외
  - 새로 생기는 부수효과(예: 이전엔 안 하던 DB 쓰기·외부 API 호출을
    이제 함)
- 호출부가 이 변경으로 깨진다면, 그 호출부도 함께 수정 범위에 포함시킨다
  (5w1h 문서의 Where에 없었더라도) — 발견하는 즉시 사용자에게 "호출부인
  `X`도 같이 수정이 필요합니다"라고 알린다.
- 한 단계 더 나아가 그 호출부를 또 사용하는 상위 계층(예: 이 서비스를
  쓰는 컨트롤러)까지 사이드이펙트가 전파되는지도 확인한다.
- 이 항목은 새로 만드는 코드(기존에 아무도 호출하지 않는 신규 함수)에는
  해당하지 않는다 — 기존 코드를 변경/대체할 때만 적용한다.

## 9. 하위 호환성

- 기존 API의 요청/응답 스펙을 변경하는 경우, 기존 호출자(다른
  프로젝트/시스템)에 영향이 있는지 5w1h 문서의 Where(외부 연동) 섹션을
  다시 확인한다.

## 10. 새로 짜는 코드의 중복·가독성 (1번과 다름 — 1번은 "기존 코드 재사용",
    이 항목은 "지금 짜는 코드 자체"의 품질)

- **중복(DRY)**: 이번에 새로 작성하는 코드 안에서 같은 로직이 2번 이상
  반복되면 메서드/함수로 추출한다. 파일 여러 개에 걸쳐 비슷한 로직을
  거의 그대로 복붙하지 않는다.
- **단일 책임**: 메서드/함수 하나가 여러 가지 일(예: 검증+조회+가공+저장을
  전부)을 다 하고 있으면, 프로젝트의 기존 분리 단위(계층/메서드 크기
  관례)에 맞춰 나눈다 — 다만 기존 코드 스타일이 원래 크게 짜는 편이면
  그 컨벤션을 존중하고 이 스킬만 유별나게 잘게 쪼개지 않는다.
- **네이밍**: 축약어·의미 없는 이름(`data`, `temp`, `a`, `flag2`)을 피하고
  의도가 드러나는 이름을 쓴다. 프로젝트의 기존 네이밍 관례(1단계에서
  확보)를 그대로 따른다.
- **매직 넘버/문자열**: 의미 있는 상수는 하드코딩하지 않고, 프로젝트에
  이미 상수 관리 방식(enum, static final, 설정값 등)이 있으면 그걸
  따른다.
- **과도한 중첩**: if/for가 3단 이상 중첩되면, 조기 반환(early return)이나
  가드 절로 풀 수 있는지 검토한다 — 프로젝트 기존 코드가 이미 깊은
  중첩 스타일이면 억지로 바꾸지 않는다.
- 이 항목은 "새 스타일 도입 금지" 원칙(2번)과 충돌하지 않는다 — 프로젝트
  컨벤션 범위 안에서 **불필요하게 지저분하게 짜지 않는다**는 뜻이지,
  이 스킬만의 새로운 규칙을 강요하는 게 아니다.
