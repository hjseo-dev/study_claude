# backend-dev 사용법

`5w1h` 스킬이 만든 분석 문서를 바탕으로, 그 계획대로 실제 백엔드 코드를
구현하는 스킬입니다. 별도 API 키나 외부 서비스 설정이 필요 없습니다.

> 이 스킬은 항상 `5w1h` 분석 문서를 재료로 삼습니다. 해당 작업의 분석
> 문서가 없으면, 대화 내용만으로 임의로 구현하지 않고 먼저 `5w1h` 분석부터
> 진행할지 물어봅니다.

## 1. 호출 방법

자동으로는 실행되지 않습니다 (`disable-model-invocation: true`). 항상
명시적으로 불러야 합니다:

```
/wlabs:backend-dev
```

## 2. 사용 흐름

1. **원본 확인**: `docs/5w1h/`에서 이번 작업에 해당하는 분석 문서를
   찾습니다. 없으면 먼저 `/wlabs:5w1h`를 진행할지 물어봅니다.
2. **프로젝트 컨벤션 확보**: `docs/STRUCTURE.md`가 있으면 그 컨벤션을,
   없으면 먼저 `/wlabs:project-struct`를 실행해 확보합니다. **언어/
   프레임워크 버전과 이미 추가된 라이브러리·플러그인을 매니페스트 파일
   (`pom.xml`/`build.gradle`/`package.json` 등)로 직접 재확인**하고, 그
   버전에서 안 되는 문법을 쓰거나 확인 없이 새 의존성을 추가하지
   않습니다. 컨벤션 표만으로 세부 스타일이 부족하면 실제로 수정할
   파일과 같은 계층의 기존 파일을 직접 읽어서 보완합니다. `.claude/`
   폴더 아래 팀이 직접 넣어둔 추가 설계·분석 문서가 있으면(설정용
   폴더는 제외) 그것도 함께 확인합니다.
3. **구현 계획 확인 (조사 먼저, 질문은 그다음)**: 변경할 파일 목록을
   정리하고, 기존 유사 기능의 코드를 먼저 읽어서 패턴과 애매함을 최대한
   스스로 해소합니다. 그렇게 조사해도 남는 애매함(로직 상세, 예외 처리,
   파라미터 형식 등)만 그때 질문합니다 — 조사로 풀릴 걸 미리 묻지
   않습니다.
4. **코드 구현**: `references/implementation-checklist.md`(트랜잭션
   경계·입력검증·에러처리·인증인가·기존 코드 재사용 등)를 따라 프로젝트
   기존 컨벤션 그대로 구현하고, 수정한 위치마다 왜 이렇게 했는지 상세
   주석을 남깁니다. **기존 함수/메서드를 고치는 경우** 호출부를 `Grep`으로
   찾아 이번 변경이 호출부를 깨뜨리지 않는지 확인합니다(새로 만드는
   코드에는 해당 없음). 파일 5개 이상 건드리는 큰 변경이면 중간에 한 번
   진행상황을 공유하고 계속할지 확인합니다.
5. **자체 검증**: 컴파일/빌드를 확인합니다(항상, 실패하면 단순 실수는
   스스로 고치고 원인 불명확하면 그대로 보고). 통과하면 **`/wlabs:code-review`를
   자동으로 이어서 실행**해서 지금까지의 변경사항을 상세히 리뷰합니다 —
   Critical/Medium 발견은 그 자리에서 바로 반영하고 다시 컴파일 확인,
   Low 발견은 반영하지 않고 목록만 남깁니다. 테스트는 사용자가 요청했을
   때만 진행하며, 기존 테스트 리포트/코드가 있어도 **그 이후 코드가
   바뀌었으면 stale로 보고** `/wlabs:test-case-creator`로 새로 만든 뒤
   실행합니다. 의미 있는 테스트가 없는 프로젝트면 컴파일 확인만으로
   충분하다고 안내합니다.
6. **완료 보고**: 변경 파일 목록과 **왜 이렇게 구현했는지 근거**(접근방법이
   여러 개였다면 선택 이유, 참고한 기존 코드 등)를 함께 정리합니다.
   반영한 리뷰 항목, 반영 안 한 Low 항목(지금 반영할지 다시 물어봄)도
   정리합니다. 새 API를 추가/변경했다면 `docs/API.md` 갱신 여부를,
   STRUCTURE.md가 실제와 달라진 게 발견됐다면 `project-struct` 재실행
   여부를 물어보고, 테스트가 더 필요하면 `/wlabs:test-case-creator`를
   쓸 수 있다고 언급만 합니다(5번에서 이미 테스트를 요청한 경우는 예외).

## 3. 결과에서 주의할 점

- 5w1h 분석 문서 없이 임의로 구현하지 않습니다 — 대화 중 배경 설명만으로
  바로 코드를 쓰지 않습니다.
- 구현 정보가 애매하면 추측하지 않고 먼저 질문합니다.
- 프로젝트 컨벤션을 무시한 새 스타일을 도입하지 않습니다 — 기존 비슷한
  기능의 코드 구조를 그대로 따릅니다. `STRUCTURE.md`만으로 부족하면 실제
  파일을 확인합니다.
- 수정/생성한 코드 위치마다 왜 그렇게 했는지 상세 주석이 남습니다(이
  스킬만의 기본값 — 다른 스킬의 "주석 최소화" 원칙과 다릅니다).
- 기존 함수를 수정할 때는 그 함수 자체만이 아니라 **호출부까지 확인**한
  뒤 진행합니다 — 필요하면 호출부도 같이 수정 범위에 포함시킵니다.
- 검증(컴파일/코드리뷰/테스트) 없이 "완료"라고 보고하지 않습니다. 컴파일
  확인과 코드 리뷰는 항상 하고, 테스트는 요청했을 때만 돌립니다.
- 코드 리뷰에서 나온 Critical/Medium은 반영 여부를 다시 묻지 않고 바로
  고칩니다 — 실제 버그를 안은 채로 "완료"라고 하지 않기 위해서입니다.
  Low는 목록만 보여주고 반영 여부를 물어봅니다.
- 테스트를 요청했는데 케이스 문서가 없으면, 조용히 기존 테스트만 돌리고
  끝내지 않고 `test-case-creator`부터 실행합니다.

## 4. 자주 겪는 문제

- **5w1h 분석 문서를 못 찾음**: `docs/5w1h/` 폴더가 없거나 여러 건이
  있어서 어떤 건지 특정이 안 될 때입니다 — 어떤 작업 건인지 알려주거나,
  먼저 `5w1h` 분석부터 진행하겠냐는 질문에 "예"라고 답하면 됩니다.
- **프론트엔드 작업도 같이 필요함**: 이 스킬은 백엔드 구현만 담당합니다.
  프론트엔드 스킬은 아직 없어서, 필요하면 별도로 알려주세요.
- **구현만 하고 테스트는 안 돌림**: 의도된 동작입니다 — 테스트는 명시적으로
  요청해야 돌립니다. 요청하면 케이스 문서 유무를 먼저 확인하고, 없으면
  `test-case-creator`를 자동으로 먼저 실행합니다.
- **코드 리뷰가 반영할지 안 물어보고 바로 고쳐짐**: 의도된 동작입니다 —
  Critical/Medium은 자동으로 바로 반영합니다. Low만 목록으로 남기고
  반영 여부를 물어봅니다.
- **테스트를 또 요청했는데 케이스를 다시 만듦**: 이전 테스트 이후 코드가
  바뀌었기 때문입니다 — 오래된 리포트로 "통과"라고 오판하지 않으려고
  최신 코드 기준으로 다시 만듭니다.

## 5. 개선/확장 아이디어

- 아직 실전 사용 데이터가 없어서, 구현 체크리스트 항목이 실제로 얼마나
  도움이 되는지는 여러 프로젝트에 써보면서 다듬어질 수 있습니다.
- 프론트엔드 구현을 담당하는 대응 스킬(`frontend-dev`)이 아직 없습니다 —
  필요해지면 이 스킬과 대등한 구조로 별도로 만들 예정입니다.
- 여러 파일을 동시에(병렬로) 구현해야 하는 대규모 변경에 대한 처리는
  아직 순차 진행만 지원합니다.
