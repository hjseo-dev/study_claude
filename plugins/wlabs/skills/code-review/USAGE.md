# code-review 사용법

지정한 브랜치의 git diff를 리뷰해서 실제로 문제가 되는 결함을 찾아내고,
원하면 바로 코드에 반영까지 하는 스킬입니다. 별도 API 키나 외부 서비스
설정이 필요 없습니다.

> **클로드 내장 `/code-review`와 다릅니다.** 내장 커맨드는 최상위
> 슬래시 커맨드라서 스킬 안에서 호출할 수 없어, 그 방법론(2단계
> 발견-검증, 구체적 실패 시나리오 요구, correctness 중심)을 참고하되
> **Critical/Medium/Low 심각도 분류(Low도 전부 보고)와 호출부·
> 사이드이펙트 추적**을 더해 이 저장소 전용으로 새로 만든 커스텀
> 스킬입니다. 더 강력한 리뷰가 필요하면 내장 `/code-review`(또는
> `/code-review ultra`)를 사용자가 직접 실행하는 것도 여전히
> 가능합니다 — 둘은 서로 대체재가 아니라 별개입니다.

## 1. 호출 방법

자동으로는 실행되지 않습니다 (`disable-model-invocation: true`). 항상
명시적으로 불러야 합니다:

```
/wlabs:code-review [브랜치명]
```

`backend-dev`는 자체 검증 단계에서 이 스킬을 **항상 자동으로**
호출합니다 — 따로 부를 필요가 없습니다. 그 경우 8번(반영 여부 확인)은
생략되고 `backend-dev`의 정책(Critical/Medium은 바로 반영, Low는 보고만)을
따릅니다. 독립적으로 다른 브랜치를 검토하고 싶을 때만 직접 호출하세요.

## 2. 사용 흐름

1. **대상과 모드 확정**: 인자로 다른 브랜치를 주면 그 브랜치를
   **커밋 대 커밋**으로 비교(3-dot diff)합니다. 인자가 없거나 현재
   브랜치를 가리키면 **작업트리 모드**로, base 대비 지금까지의 모든
   변경을 커밋 여부와 무관하게 봅니다(`backend-dev`가 부르는 경우가 이
   모드입니다). base(main/master)는 자동 감지합니다.
2. **변경 범위 확보**: 위 모드에 맞는 diff로 누적 변경 전체를 봅니다
   (마지막 커밋/저장만 보지 않습니다).
3. **프로젝트 컨텍스트 확보**: `docs/STRUCTURE.md`(없으면 먼저
   `project-struct` 실행)와, 백엔드 코드라면
   `backend-dev`의 구현 체크리스트도 참고합니다.
4. **호출부·사이드이펙트 확보**: diff에서 시그니처/동작이 바뀐 코드가
   있으면, diff 밖의 파일까지 `Grep`으로 호출부를 찾아 영향을 확인합니다.
5. **1차 발견**: correctness·side-effect를 중심으로, security/
   test-coverage/efficiency/simplification 관점에서 후보를 넓게
   찾습니다.
6. **2차 검증 및 심각도 분류**: 각 후보를 실제 코드·호출부와 대조해서
   확인된 것만 남기고, 신뢰도(CONFIRMED/PLAUSIBLE)와 심각도(Critical/
   Medium/Low)를 매깁니다. test-coverage·simplification은 그 자체로
   Critical이 될 수 없습니다.
7. **보고**: `ReportFindings` 도구로, 구체적 실패 시나리오와 `file:line`
   근거를 담아 Critical→Medium→Low 순으로 **Low를 포함해 전부**
   보고합니다.
8. **반영 여부 확인** (독립 호출일 때만): 지금 바로 반영할지 묻고,
   반영하면 수정 후 다시 컴파일/빌드로 재검증합니다.

## 3. 결과에서 주의할 점

- 기본은 correctness(실제 버그) + side-effect(호출부 영향)를 다룹니다
  — 스타일/포맷팅 지적은 하지 않습니다.
- 확신 없는 지적은 CONFIRMED가 아니라 PLAUSIBLE로 표시됩니다(심각도와는
  별개 축입니다).
- **Low 심각도도 전부 보고됩니다** — 확신이 낮아서가 아니라 영향이
  작을 뿐이므로 숨기지 않습니다. 카테고리 자체가 해당 없으면(예: 이번
  diff에 security 이슈가 없음) 그 카테고리만 안 나올 수 있습니다.
- 시그니처/동작이 바뀐 코드는 diff에 없는 파일(호출부)까지 확인합니다.
- 반영은 항상 먼저 물어본 뒤에만 진행됩니다 — 리뷰만 보고 끝낼 수도
  있습니다.

## 4. 자주 겪는 문제

- **target과 base가 같음**: 아직 기능 브랜치를 안 딴 상태(예: base에서
  바로 작업 중)라는 뜻입니다 — 이 스킬은 항상 브랜치 작업을 전제로 하므로
  실제 상황을 다시 확인합니다.
- **backend-dev가 부를 때 "반영할까요?" 질문이 안 나옴**: 의도된
  동작입니다 — 그때는 Critical/Medium을 자동으로 바로 반영하고 Low만
  목록으로 남깁니다. 독립적으로(`/wlabs:code-review` 직접 호출) 실행하면
  평소처럼 반영 여부를 먼저 물어봅니다.
- **`docs/STRUCTURE.md`가 없어서 project-struct부터 돎**: 처음 한 번만
  겪는 비용이고, 이후로는 재사용됩니다.
- **테스트 코드가 없다고 나왔는데 안 만들어줌**: 의도된 동작입니다 —
  이 스킬은 "테스트가 없다"는 사실만 지적하고, 실제 테스트 작성은
  `/wlabs:test-case-creator`가 담당합니다.
- **사소해 보이는 Low 항목까지 다 나옴**: 의도된 동작입니다 — 내장
  리뷰와 달리 이 스킬은 검증을 통과한 건 심각도와 무관하게 다
  보여줍니다. 심각도로 정렬돼 있으니 Critical/Medium만 먼저 보고 Low는
  나중에 봐도 됩니다.

## 5. 개선/확장 아이디어

- 아직 실전 사용 데이터가 없어서, 카테고리별 오탐률이 실제로 어느
  정도인지는 여러 번 써보면서 다듬어질 수 있습니다.
- 지금은 백엔드 코드 기준 체크리스트만 참고합니다 — 프론트엔드용
  체크리스트가 생기면 그것도 함께 참고하도록 확장할 수 있습니다.
- 리뷰 강도(내장 리뷰의 low~max 같은 effort 조절)는 의도적으로 넣지
  않았습니다 — 이 스킬은 항상 "상세하고 꼼꼼하게"를 기본값으로 합니다.
