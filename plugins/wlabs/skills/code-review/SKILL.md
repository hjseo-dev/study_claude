# code-review — git diff 기반 코드 리뷰 및 반영

지정한 브랜치가 base 브랜치 대비 만든 변경사항을 리뷰해서, 실제로
문제가 되는 결함을 찾아 `ReportFindings` 도구로 보고하고, 원하면 그
자리에서 수정까지 반영한다.

방법론(호출부·사이드이펙트 추적, 2단계 발견-검증, 신뢰도 판단, Critical/
Medium/Low 심각도 분류, 카테고리 정의)은
[references/review-methodology.md](references/review-methodology.md)에
정리되어 있다 — 리뷰 시작 전에 반드시 읽는다.

> `backend-dev`는 자체 검증 단계에서 이 스킬을 **항상 자동으로**
> 호출한다(작업트리 모드) — 그 경우 7번(반영 여부 확인)은 건너뛰고
> `backend-dev` 자신의 정책(Critical/Medium 자동 반영, Low는 보고만)을
> 따른다. 이 스킬을 독립적으로 쓸 때(예: 다른 브랜치 검토)는 0~7번을
> 그대로 다 수행한다.

## 0. 인자 파싱: 비교 대상과 모드 결정

이 스킬을 쓰는 프로젝트는 항상 기능 브랜치를 따서 작업하는 것을 전제로
한다(master/main에서 직접 작업하지 않음).

- `$ARGUMENTS`가 있고 그게 **현재 체크아웃된 브랜치가 아니면**: 그
  브랜치를 target으로 삼고 **커밋 대 커밋 모드**로 진행한다 — 이미 다
  끝나서 커밋된, 지금 내가 체크아웃하지 않은 다른 브랜치를 검토하는
  경우다(예: 동료 브랜치 리뷰).
- `$ARGUMENTS`가 없거나 현재 체크아웃된 브랜치를 가리키면: **작업트리
  모드**로 진행한다 — base 대비 지금까지의 모든 변경을 커밋 여부와
  무관하게 본다. `backend-dev`가 개발 도중/직후에 이어서 부르는 경우가
  이 모드다(기본값).
- target 브랜치(커밋 대 커밋 모드)가 로컬에 없으면 존재하는 브랜치
  목록(`git branch -a`)을 보여주고 사용자에게 다시 물어본다 — 추측으로
  비슷한 이름을 골라 진행하지 않는다.

**base 브랜치 자동 감지**: `git rev-parse --verify --quiet main`이
성공하면 `main`, 실패하면 `master`를 시도한다. 둘 다 없으면
`git branch -a` 결과를 보여주고 base 브랜치를 사용자에게 물어본다.

작업트리 모드에서 현재 브랜치가 base와 같으면(아직 브랜치를 안 딴
상태) 사용자에게 확인한다 — 이 스킬의 전제(항상 브랜치 작업)와 어긋나는
상황이므로 추측하지 않는다.

## 1. 변경 범위 확보

**커밋 대 커밋 모드** — merge-base 기준 3-dot diff로 전체 누적 변경을
한 번에 잡는다:

```
git log <base>..<target> --oneline          # 포함되는 커밋 목록
git diff <base>...<target> --name-status     # 변경 파일 목록 (A/M/D)
git diff <base>...<target> -- <파일>          # 파일별 상세 diff
```

**작업트리 모드** — base 대비 지금 작업트리 상태(커밋+미커밋 전부)를
그대로 본다:

```
git diff <base> --name-status                # base 대비 변경 파일 (커밋 여부 무관)
git diff <base> -- <파일>                      # 파일별 상세 diff (미커밋 포함)
```

두 모드 모두, 파일이 많으면 `--name-status`로 먼저 전체 목록을 파악한
뒤, 실제 로직이 바뀐 파일(설정/락파일/생성된 파일 제외)만 골라 상세
diff를 확인한다.

## 2. 프로젝트 컨텍스트 확보

`docs/STRUCTURE.md`가 있는지 확인한다.

- **있으면** 그 문서(및 `docs/API.md`)로 기술 스택과 컨벤션을 파악한다.
- **없으면** 먼저 `Skill` 도구로 `wlabs:project-struct`를 실행해 생성한 뒤
  이어서 진행한다.
- **언어/프레임워크 버전과 기존 의존성 확인 (항상)**: `docs/STRUCTURE.md`의
  기술 스택 표를 1차로 참고하되, 실제 매니페스트 파일(`pom.xml`/
  `build.gradle`/`package.json` 등)을 `Read`해서 정확한 버전과 이미 추가된
  라이브러리·플러그인을 재확인한다. 반영(7번)할 때 이 버전에서 안 되는
  문법/API를 제안하거나, 확인 없이 새 의존성이 필요한 수정을 반영하지
  않는다 — 새 의존성이 꼭 필요하면 반영 전에 사용자에게 확인한다.
- 리뷰 대상이 백엔드 코드이고 `../backend-dev/references/implementation-checklist.md`가
  있으면, 그 체크리스트(트랜잭션 경계·입력검증·에러처리·인증인가·민감정보·
  성능·하위호환)도 correctness 판단 기준에 포함한다.
- **`.claude/` 아래 추가 참고 문서 확인**: 팀이 직접 넣어둔 설계·분석
  문서가 있을 수 있다. `Glob`으로 `.claude/**/*.md`(`.claude/skills/`·
  `.claude/commands/`·`.claude/agents/` 같은 Claude Code 설정용 폴더는
  제외)를 확인하고, 이번 diff와 관련 있어 보이는 파일만 `Read`해서
  판단 기준(특히 이 프로젝트만의 규칙·제약)에 반영한다. 없으면 그냥
  넘어간다.
- **STRUCTURE.md가 실제와 다르면 갱신을 제안한다**: 위 과정에서
  STRUCTURE.md 내용이 실제 코드와 다른 걸 발견하면, 조용히 우회만 하지
  말고 6번(보고)에서 `project-struct` 재실행을 제안한다.

## 3. 호출부·사이드이펙트 확보 (diff 밖까지 본다)

diff만 보고 끝내지 않는다 — **diff에 없는 파일에서 문제가 생길 수 있는
지점**을 먼저 확보해야 다음 단계에서 제대로 검증할 수 있다.

1. diff에서 시그니처(파라미터, 반환 타입)나 동작(부수효과, 예외 발생
   조건, 반환값 의미)이 바뀐 함수·메서드·클래스 멤버를 추린다.
2. 각각에 대해 `Grep`으로 프로젝트 전체에서 호출부를 찾는다.
3. 찾은 호출부를 `Read`해서, 그 호출부가 **기존 동작을 전제로 하고
   있는지** 확인한다 — 예: 예전엔 null을 반환하던 함수가 이제 예외를
   던지면, null 체크만 하던 호출부는 처리 안 된 예외로 깨진다.
4. 이 함수/메서드를 거쳐 영향받는 다른 계층(예: 이 서비스 메서드를 쓰는
   컨트롤러, 이 DAO를 쓰는 다른 서비스)까지 한 단계 더 따라가서 사이드
   이펙트가 전파되는지 확인한다.
5. 여기서 확보한 호출부 목록과 사용 맥락은 다음 단계(1차 발견, 2차 검증)
   전체에서 계속 참고한다.

## 4. 1차 발견 (여러 관점에서 후보 탐색)

diff, 3번에서 확보한 호출부, 필요시 그 주변 코드(`Read`)를 보고, 아래
관점에서 **후보**를 찾는다(아직 확정하지 않는다):

- **correctness (기본, 최우선)**: 실제로 잘못된 동작 — null/경계값
  처리 누락, 조건 반전, 오프바이원, 잘못된 예외 처리, 트랜잭션 경계 오류,
  동시성 문제 등
- **side-effect**: 3번에서 찾은 호출부가 이번 변경으로 깨지거나, 의도치
  않은 부수효과(예: 이제 DB에 쓰기가 발생함, 이제 예외를 던짐)가
  호출부에 전파되는 경우
- **security**: 인증/인가 누락, 입력 검증 누락으로 인한 injection, 민감정보
  노출
- **test-coverage**: 이 diff가 만든 새 분기/예외 케이스에 대응하는 테스트가
  없음 (있는지 여부만 확인 — 테스트 작성 자체는 `test-case-creator`의
  역할)
- **efficiency**: 반복문 안 DB/API 호출(N+1), 불필요한 전체 로딩
- **simplification**: 과도하게 복잡한 구현, 이미 있는 유틸/패턴을 무시한
  중복 코드

카테고리별로 억지로 다 채우지 않는다 — 이번 diff에 해당 없는 관점은
후보가 없을 수 있다(정상). 단, **side-effect는 3번에서 시그니처/동작이
바뀐 대상이 하나라도 있었다면 반드시 검토를 거친다** — 후보가 없다는
결론도 "확인했지만 없음"으로 남긴다.

## 5. 2차 검증 (후보를 실제 코드와 대조) 및 심각도 분류

1차에서 나온 각 후보에 대해:

1. 관련 코드와 3번에서 확보한 호출부를 실제로 `Read`해서 그 결함이
   **정말로 이 입력/상태에서 발생하는지** 확인한다 — 코드를 안 보고
   diff 텍스트만으로 짐작하지 않는다.
2. 확실히 재현 가능하면 `verdict: CONFIRMED`.
3. 재현 경로가 그럴듯하지만 100% 확신은 안 서면(예: 호출부를 다 못
   확인함) `verdict: PLAUSIBLE`.
4. 실제로 확인해보니 문제가 아니면(예: 이미 상위에서 처리됨) 후보에서
   제외한다 — 억지로 보고하지 않는다.
5. 사소한 스타일 지적(포맷팅, 변수명 취향)은 여기서 걸러낸다 — 이건
   심각도와 무관하게 애초에 리뷰 대상이 아니다.
6. 살아남은(CONFIRMED/PLAUSIBLE) 각 후보에 **심각도**를 매긴다:
   - **Critical**: 데이터 손실/손상, 보안 침해, 서비스 중단(크래시·
     무한루프·데드락), 트랜잭션 무결성 파괴 — 실서비스에 즉시 영향
   - **Medium**: 특정 조건/입력에서만 오동작, 일부 케이스·일부 호출부만
     영향받음, 무시할 수 없는 성능 저하
   - **Low**: 드문 엣지케이스, 영향 범위가 작거나 사용자에게 거의 안
     보임, 지금 당장 장애는 아니지만 고쳐두면 좋은 것
   - **test-coverage·simplification은 그 자체로 Critical이 될 수 없다**
     (실제 장애가 아니라 관리상 아쉬운 점이므로) — 상세 기준은
     `references/review-methodology.md`의 5-1 참고.

## 6. 보고 (모든 심각도 포함)

`ReportFindings` 도구로 보고한다. **Critical → Medium → Low 순으로
정렬**하고, **Low로 분류된 것도 누락 없이 전부 포함한다** — 확신이
낮아서가 아니라 영향이 작아서 낮은 우선순위일 뿐, 검증(5번)을 통과한
것은 전부 보고한다. `short_summary`에 `[Critical]`/`[Medium]`/`[Low]`
태그를 앞에 붙여서 한눈에 심각도를 알 수 있게 한다.

각 finding은 **구체적인 실패 시나리오**(어떤 입력/상태에서 → 어떤
잘못된 결과/크래시)와 `file`/`line`을 반드시 포함한다 — "이 부분이
불안해 보인다" 식의 막연한 지적은 하지 않는다. side-effect 카테고리
finding은 실패 시나리오에 **어느 호출부가 어떻게 영향받는지**(파일:줄
포함)를 명시한다.

발견된 게 하나도 없으면(Critical/Medium/Low 전부 0건) 빈 배열로
보고하고, "호출부·사이드이펙트까지 확인했지만 문제 없음"이라고
명시한다.

2번에서 STRUCTURE.md가 실제와 다른 걸 발견했다면, 이 보고와 함께
`project-struct` 재실행을 제안한다.

## 7. 반영 여부 확인

**`backend-dev`가 자체 검증 단계에서 이 스킬을 호출한 경우, 이 단계는
건너뛴다** — 대신 `backend-dev`의 정책(Critical/Medium 자동 반영, Low는
보고만)을 따른다. 이 스킬을 독립적으로 호출했을 때만 아래를 수행한다.

보고 후 `AskUserQuestion`으로 물어본다: "발견된 N개 항목을 지금 바로
반영할까요?" (전체 반영 / 골라서 반영 / 반영 안 함).

- **전체/일부 반영을 선택하면**: 해당 항목을 수정하고, 수정한 부분에는
  `backend-dev`와 동일하게 왜 고쳤는지 주석을 남긴다.
- 수정 후 `ReportFindings`를 다시 호출해 각 finding에 `outcome`
  (`fixed`/`skipped`/`no_change_needed`)을 채워 재보고한다.
- 수정 후에는 컴파일/빌드 확인을 다시 한다 — 고치다가 새 오류를 만들지
  않았는지 확인 없이 끝내지 않는다.

## Anti-patterns

- 검증(5번) 없이 1차 발견 후보를 그대로 보고하지 않는다 — 반드시 실제
  코드로 재확인한다.
- **매니페스트 파일을 확인하지 않고 언어/프레임워크 버전을 짐작한 채로
  수정을 반영하지 않는다** — 반영 전 실제 버전/기존 의존성을 재확인한다.
- STRUCTURE.md가 실제와 다른 걸 발견하고도 보고에서 갱신 제안을 빠뜨리지
  않는다.
- **diff에 나온 파일만 보고 끝내지 않는다** — 시그니처/동작이 바뀐
  대상이 있으면 호출부(diff 밖의 다른 파일)까지 반드시 추적한다.
- 확신 없는 지적을 CONFIRMED로 부풀리지 않는다 — 애매하면 PLAUSIBLE.
- **Low 심각도라고 보고에서 빼지 않는다** — 검증을 통과했으면 Critical/
  Medium/Low 가리지 않고 전부 보고한다. 다만 심각도와 무관하게 스타일/
  포맷팅 지적은 애초에 리뷰 대상이 아니다.
- 구체적 실패 시나리오와 `file:line` 없이 막연하게 지적하지 않는다.
- 반영 여부를 묻지 않고 마음대로 코드를 고치지 않는다 (`backend-dev`가
  호출한 경우는 예외 — 그쪽 정책을 따른다).
- 수정 후 재검증(컴파일) 없이 끝내지 않는다.
