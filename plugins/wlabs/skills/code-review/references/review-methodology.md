# 리뷰 방법론

Claude Code 내장 `/code-review`(및 `ultra`)의 방법론을 조사해서 이 저장소
전용 커스텀 스킬에 적용한 것이다. 이 문서는 그 방법론을 요약한다.

## 1. 기본은 correctness — 스타일은 다루지 않는다

내장 리뷰의 기본값은 "실제로 프로덕션에서 터지는 버그"만 찾는 것이다.
포맷팅, 변수명 취향 같은 스타일 지적은 기본 범위에서 제외한다. 이 스킬도
같은 원칙을 따른다 — 확인 필요 사항이 스타일뿐이면 보고하지 않는다.

## 2. 발견과 검증을 분리한다 (2단계)

1. **발견(discovery)**: diff를 보고 여러 관점(correctness/security/
   test-coverage/efficiency/simplification)에서 "이거 문제일 수도 있다"는
   후보를 최대한 넓게 찾는다.
2. **검증(verification)**: 각 후보를 실제 코드(호출부, 주변 로직)와
   대조해서 "정말로 이 입력/상태에서 발생하는가"를 확인한다. 이 단계를
   건너뛰면 오탐(false positive)이 그대로 보고돼서 신뢰도가 떨어진다.

발견 단계에서 넓게, 검증 단계에서 좁게 — 이 순서를 바꾸지 않는다(먼저
확신 있는 것만 찾으려 하면 애초에 후보 목록이 좁아져서 놓치는 게 생긴다).

## 3. 신뢰도 표시: CONFIRMED vs PLAUSIBLE

검증 결과에 따라 신뢰도를 구분해서 보고한다(무조건 확정처럼 말하지
않는다):

- **CONFIRMED**: 실제 코드를 따라가서 결함이 발생하는 경로를 구체적으로
  확인함
- **PLAUSIBLE**: 발생 가능성은 있으나 호출부를 전부 확인하지 못했거나
  런타임 상태에 따라 달라질 수 있어 100% 확신은 어려움

확신이 안 서는 걸 CONFIRMED로 부풀리지 않는다 — 과장된 확신은 나중에
신뢰를 잃는다.

## 4. 구체적 실패 시나리오가 없으면 보고하지 않는다

"이 부분이 안전하지 않아 보인다" 같은 막연한 지적은 하지 않는다. 항상
**"어떤 입력/상태에서 → 어떤 잘못된 결과/크래시가 나는지"**를 구체적으로
적고, 근거가 되는 `file:line`을 남긴다. 이렇게 못 채우겠으면 애초에
후보에서 제외한다(추측성 지적이라는 뜻이므로).

## 5. 지적 개수를 억지로 늘리지 않는다 (단, 검증을 통과한 건 다 보고한다)

카테고리마다 최소 1개씩 채우려고 지어내지 않는다. 이번 diff에 해당 없는
관점은 후보가 아예 없는 게 정상이다.

**단, 이 스킬은 내장 리뷰의 "확신 낮은 건 걸러서 적게 보여준다"는
기본값을 그대로 따르지 않는다.** 검증(3번)을 통과한 것(CONFIRMED/
PLAUSIBLE)이면 심각도가 Low라도 전부 보고한다 — "이건 사소하니 굳이
말 안 해도 되겠지"라고 스스로 판단해서 누락하지 않는다. 대신 심각도로
우선순위를 표시해서, 보는 사람이 Critical부터 처리하고 Low는 나중에
보거나 무시할지 스스로 고르게 한다.

억지로 늘리지 않는다는 것과 검증된 건 다 보여준다는 것은 다른 이야기다
— 전자는 "지어내지 않는다", 후자는 "찾은 건 숨기지 않는다"는 뜻이다.

**이 스킬은 "짧고 확신 있는 리뷰"보다 "상세하고 꼼꼼한 리뷰"를
우선한다.** 시간·비용을 아끼려고 후보 탐색 범위를 좁히거나, 호출부
확인을 1~2곳만 하고 멈추거나, 애매하면 아예 후보에서 빼버리는 식으로
스스로 검토를 축소하지 않는다 — 애매한 건 PLAUSIBLE로 분류해서라도
보고한다(단, 3번·4번의 검증·근거 요건은 그대로 지킨다 — "상세하게"가
"근거 없이 많이"를 뜻하지는 않는다).

## 5-1. 심각도(Critical/Medium/Low) 분류 기준

- **Critical**: 데이터 손실/손상, 보안 침해(인증·인가 우회, 민감정보
  노출), 서비스 중단(크래시·무한루프·데드락), 트랜잭션 무결성 파괴 —
  실서비스에 즉시 영향을 준다.
- **Medium**: 특정 조건·입력에서만 발생하는 오동작, 일부 사용자·일부
  호출 경로에만 영향, 무시하기 어려운 성능 저하, 일부 호출부에서만
  깨지는 사이드이펙트.
- **Low**: 발생 조건이 드문 엣지케이스, 영향 범위가 매우 좁거나
  사용자에게 거의 드러나지 않음, 당장 장애는 아니지만 고쳐두면 좋은
  것.

심각도는 confidence(CONFIRMED/PLAUSIBLE)와 **다른 축**이다 — "얼마나
확실한가"와 "얼마나 심각한가"는 독립적으로 판단한다(예: 발생 조건은
확실하지만 영향은 미미한 PLAUSIBLE-Low도 있을 수 있고, 발생은 드물지만
한 번 터지면 치명적인 CONFIRMED-Critical도 있을 수 있다).

**test-coverage·simplification 카테고리의 심각도 상한**: 이 두
카테고리는 "지금 이미 터지는 결함"이 아니라 "관리상 아쉬운 점"이므로,
그 자체만으로는 **Critical이 될 수 없다** (Critical은 데이터/보안/서비스
중단처럼 실제 장애를 뜻하는 등급이다):

- **test-coverage**: 새로 생긴 분기가 결제·인증처럼 중요한 로직이면
  Medium, 그 외(단순 분기, 로그성 코드 등)면 Low.
- **simplification**: 유지보수를 실제로 어렵게 만들 정도로 복잡하거나
  중복이 크면 Medium, 그 정도가 아니면 Low.
- 단, correctness·side-effect·security 관점에서 **동시에** 문제가
  있다면(예: 테스트가 없어서 이미 확인된 버그를 못 잡고 있었다) 그
  correctness/side-effect/security 쪽 심각도를 따로 매겨서 별개
  finding으로 보고한다 — test-coverage 항목 자체의 등급을 올리지 않는다.

## 5-2. 호출부·사이드이펙트는 diff 밖까지 본다

diff에 나온 파일만 보고 "이 함수 안에서는 문제 없음"이라고 끝내지
않는다. 함수·메서드의 시그니처나 동작(부수효과, 예외, 반환값 의미)이
바뀌었다면, 그 대상을 실제로 **누가 호출하는지**(`Grep`으로 찾음)까지
확인해야 진짜 영향 범위를 알 수 있다. 이 확인은 diff에 포함되지 않은
파일까지 열어봐야 하는 경우가 대부분이다 — diff 범위 안에서만 검증을
끝내면 정작 실제로 깨지는 지점(호출부)을 놓친다.

이 원칙은 리뷰뿐 아니라 **코드를 새로 작성/수정하는 단계(`backend-dev`)
에도 동일하게 적용된다** — 기존 함수를 고칠 때는 그 함수만 보지 말고
호출부까지 같이 확인해야 한다.

## 6. 카테고리 정의

- **correctness**: 실제로 틀린 동작(로직 오류, 예외 처리 누락, 트랜잭션
  경계 오류, 동시성 문제 등)
- **side-effect**: 시그니처/동작이 바뀐 코드의 호출부가 이번 변경으로
  깨지거나, 의도치 않은 부수효과가 호출부·연관 모듈로 전파되는 경우
- **security**: 인증/인가 누락, 입력검증 미비로 인한 injection, 민감정보
  노출
- **test-coverage**: 이 diff가 만든 새 분기/예외 케이스에 대응 테스트가
  없음 (테스트 작성은 이 스킬이 아니라 `test-case-creator`가 담당)
- **efficiency**: N+1 쿼리, 불필요한 전체 데이터 로딩 등
- **simplification**: 과도한 복잡도, 기존 유틸/패턴을 무시한 중복 구현

## 7. 수정 반영 시 원칙

- 이 스킬을 **독립적으로** 호출했을 때는 반영 여부를 항상 먼저 물어본다
  — 리뷰와 수정은 별개의 의사결정이다.
- `backend-dev`가 자체 검증 단계에서 이 스킬을 호출한 경우는 예외다 —
  그때는 `backend-dev`의 정책(Critical/Medium은 바로 반영, Low는 보고만)을
  따르고 이 스킬의 반영 여부 확인 단계는 건너뛴다.
- 수정한 위치에는 왜 고쳤는지 주석을 남긴다(`backend-dev`와 동일한 원칙).
- 수정 후에는 반드시 재검증(컴파일/빌드)한다 — 고치다가 새 오류를
  만들었을 수 있다.
