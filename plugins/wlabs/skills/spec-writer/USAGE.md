# spec-writer 사용법

신규 요구사항을 프로젝트 코드와 함께 확인해서 5W1H 방식으로 정리하고,
필요하면 Mermaid 다이어그램까지 포함한 분석 문서를 만들어주는 스킬입니다.

> 이미 있는 프로젝트/기능을 놓고 "다음에 뭘 어떻게 할지" 정리하고 싶으면
> 이 스킬 대신 `/wlabs:5w1h`를 씁니다.

## 1. 호출 방법

```
/wlabs:spec-writer
```

`/wlabs:spec-writer 로그인 실패 버그`처럼 요구사항을 인자로 바로
붙일 수도 있고, 그냥 `/wlabs:spec-writer`만 치면 대화로 물어봅니다.

자동으로는 실행되지 않습니다 (`disable-model-invocation: true`).

## 2. 사용 흐름

1. 변경 유형(버그 수정/기능 개선/신규 기능/리팩토링/성능 개선/기술 부채 해소/보안 패치/기타)을 물어봅니다.
2. 요구사항이 애매하면 대화로 바로 되묻습니다.
3. 현재 프로젝트 코드를 조사합니다 — 관련 파일, git 히스토리, 다른 프로젝트와의
   코드/인프라 결합 여부까지 확인합니다.
4. 5W1H(+변경 유형별 추가 항목: 우선순위, 범위 외, 버그면 재현절차/기대-실제결과/환경/심각도)를
   채운 문서를 만듭니다. 필요하면 Mermaid 다이어그램(기본은 시퀀스 다이어그램)도 포함합니다.
5. 분석 대상 프로젝트의 `docs/analysis/{날짜}_{제목}.md`로 저장합니다.

## 3. 변경 유형에 따라 결과물이 달라집니다

- **신규 기능**: 비슷한 기능이 이미 있는지부터 확인합니다 (재사용/일반화 제안 우선)
- **기능 개선**: "현재 동작 → 개선 후 동작"을 표로 비교합니다
- **버그 수정**: 요구 배경 대신 재현 절차·기대 결과 vs 실제 결과·환경 정보·심각도를 채웁니다

## 4. 자주 겪는 문제

- **다이어그램이 너무 단순/복잡하게 나옴**: 판단 기준(포함 여부)과 종류 선택
  기준이 `references/5w1h-template.md`에 있습니다. 범위가 넓으면 넓은
  관점(개요) + 좁은 관점(시나리오별 상세)으로 나눠서 요청해보세요.
- **다른 프로젝트 영향을 놓친 것 같음**: "이 프로젝트도 확인해줘"라고
  직접 지목하면 그 프로젝트까지 조사합니다.
- **회의/발표 대본을 검토받고 싶음**: 이 스킬이 아니라 `/wlabs:meeting-speech-review`를
  씁니다 (`5w1h`에 딸린 스킬입니다).

## 5. 개선/확장 아이디어

- 아직 실전 사용 데이터가 많지 않아서, 실제로 여러 번 써보면서 5W1H 항목
  구성(우선순위/범위외/버그전용 필드 등)이 더 다듬어질 수 있습니다.
- 다이어그램 넓은/좁은 관점 분리는 아직 실제로 "범위가 넓은" 케이스로
  테스트해본 적이 없습니다.
- `${CLAUDE_PLUGIN_ROOT}` 같은 플러그인 상대경로 변수를 아직 안 쓰고
  있어서, 이 플러그인이 다른 컴퓨터/경로에 설치되면 일부 안내 문구의
  절대경로가 안 맞을 수 있습니다.
