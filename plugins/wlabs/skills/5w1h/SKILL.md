# 5W1H 분석 (project-struct 연계)

이미 있는 프로젝트/기능에 대해 "추가 개발", "유지보수", "버그 수정",
"여러 접근방법 중 선택", "고려해야 할 사항 검토" 중 하나를 5W1H 틀로
정리한 분석 문서를 만든다. `project-struct`가 만든 프로젝트 전체 분석을
배경지식으로 삼는다.

문서 템플릿·관점 목록·다이어그램 판단 기준은
[references/5w1h-template.md](references/5w1h-template.md)에 정리되어
있다 — 작성 전에 반드시 읽는다.

> 이 분석 내용을 회의/발표에서 말로 전달할 대본으로 다듬고 싶으면
> `/wlabs:meeting-speech-review`를 쓴다. 단, 이 스킬이 자동으로 제안하지는
> 않는다 — 사용자가 명시적으로 호출했을 때만 실행되는 별개 스킬이다.

## 0. project-struct 배경지식 확보

1. 현재 프로젝트 루트에 `docs/STRUCTURE.md`가 있는지 `Glob`으로 확인한다.
2. **있으면**: `docs/STRUCTURE.md`를 `Read`하고, 이번 주제와 관련 있어
   보이면 `docs/API.md`·`docs/EXTERNAL-SYSTEMS.md`도 함께 `Read`해서
   배경지식으로 삼는다.
3. **없으면**: 먼저 사용자에게 "이 프로젝트는 아직 project-struct 분석이
   없어서 먼저 전체 구조부터 분석하고 이어서 5W1H 분석을 진행할게요"라고
   짧게 알린 뒤, `Skill` 도구로 `wlabs:project-struct`를 실행한다. 산출물
   (`docs/STRUCTURE.md` 등)이 만들어지면 그걸 배경지식으로 이어서
   사용한다 — project-struct 산출물을 다시 요약해서 보여줄 필요는 없다.
4. **`.claude/` 아래 추가 참고 문서 확인**: 이 스킬(또는 project-struct)이
   만든 문서 외에도, 팀/프로젝트가 직접 넣어둔 분석·설계 문서가
   `.claude/` 폴더 아래 있을 수 있다. `Glob`으로
   `.claude/**/*.md`(`.claude/skills/`·`.claude/commands/`·`.claude/agents/`
   같은 Claude Code 설정용 폴더는 제외)를 확인하고, 이번 주제와 관련
   있어 보이는 파일만 `Read`해서 배경지식에 포함한다. 없으면 그냥
   넘어간다(없는 게 정상일 수 있다).

## 1. 요구사항 파악

사용자가 대화로 설명한 내용을 분석 대상으로 삼는다. Jira 티켓 본문 등을
붙여넣었으면 그대로 활용한다. 핵심이 애매하면(범위가 불명확하거나 여러
해석이 가능하면) 조사에 들어가기 전에 `AskUserQuestion`이나 일반 대화로
바로 물어본다.

## 2. 관점 확인

`references/5w1h-template.md`의 관점 목록(추가 개발/유지보수/버그 수정/
접근방법 결정/고려사항 검토/기타)을 `AskUserQuestion`으로 제시하고 고르게
한다(설명만으로 이미 명확하면 후보를 좁혀서 "이거 맞나요?" 정도로 확인).

## 3. 코드 조사

0번에서 확보한 project-struct 산출물(`docs/STRUCTURE.md`·`docs/API.md`·
`docs/EXTERNAL-SYSTEMS.md`)을 1차 소스로 삼는다. 이번 주제와 직접 관련된
부분만 골라서, 필요한 만큼만 `Grep`/`Glob`/`Read`로 추가 확인한다 — 이미
project-struct가 정리해 둔 내용을 처음부터 다시 조사하지 않는다. 관련
`git log`/`git blame`도 필요하면 확인해서 Why/When을 채우는 데 참고한다.

**단, "범위 외(Out of Scope)"나 "이 기능/모듈은 이번 작업과 무관하다"처럼
분석 결론에 직결되는 판단은 project-struct 문서 서술만 믿고 넘어가지 않는다
— 관련 코드를 실제로 `Read`해서 재확인한 뒤 결론에 반영한다.
project-struct 산출물도 최신 코드와 어긋나 있을 수 있다는 전제로 다룬다.

## 4. 5W1H 정리

`references/5w1h-template.md`의 템플릿을 그대로 따라 채운다. **요약은
5W1H를 전부 채운 다음 맨 마지막에 쓰되, 문서 안에서는 맨 위에 배치한다.**
특히:

- **Who**: 프로젝트(시스템) 관점으로 쓴다. 영향받는 다른 시스템이 있는지는
  `docs/EXTERNAL-SYSTEMS.md`를 우선 참고한다.
- **What**: 2번에서 고른 관점에 맞춰 정리한다. **관점이 "버그 수정"이면
  범위 외 대신 재현 절차·기대 결과 vs 실제 결과·환경 정보·심각도를
  채운다** — 템플릿의 버그 전용 필드 참고.
- **고려사항**: "고려사항 검토" 관점이면 문서의 핵심 섹션이므로 특히
  꼼꼼히 채운다. 다른 관점이어도 섹션 자체는 생략하지 않는다.

## 5. 문서 포맷팅 규칙

- **H1 제목**: 이번 주제에 어울리는 이모지를 하나 골라 제목 앞에 붙인다
  (문서마다 새로 고른다).
- **각 `##` 섹션 제목**: `references/5w1h-template.md`에 정해진 고정
  이모지를 그대로 쓴다(문서마다 바뀌지 않게 해서 훑어볼 때 일관되게
  한다).
- **헤딩 위계("폰트 사이즈")**: 순수 마크다운이라 실제 글자 크기를 지정할
  수 없으므로, H1(문서 제목) > H2(주요 섹션) > H3(하위 항목) 순서로 헤딩
  레벨을 정확히 지켜서 시각적 위계를 만든다. 본문 문단 중간에 이모지나
  볼드로 크기를 흉내내지 않는다 — 헤딩 레벨로만 구분한다.

## 6. 다이어그램

`references/5w1h-template.md`의 포함 기준으로 필요 여부를 판단하고,
필요하면 같은 문서의 종류 선택 표를 참고해 Mermaid 다이어그램을 문서 안에
직접 삽입한다. (별도로 HTML Artifact로 시각화/비교 자료를 만들게 되면
`../../references/visual-style.md`를 따른다 — Mermaid 자체에는 적용되지
않는다.)

## 7. 산출물 저장

분석 대상 프로젝트 루트의 `docs/5w1h/` 폴더에
`{YYYY-MM-DD}_{작업/요구사항 제목(공백은 하이픈)}.md`로 저장한다. 폴더가
없으면 만든다.

## Anti-patterns

- project-struct 산출물이 이미 있는데 그걸 무시하고 코드베이스를 처음부터
  다시 정찰하지 않는다 — 이번 주제와 관련된 부분만 추가로 확인한다.
- "고려사항" 섹션을 다른 관점(추가 개발/유지보수 등)일 때 생략하지 않는다
  — 내용이 적더라도 "특별한 고려사항 없음"으로 명시한다.
- 마크다운 문법으로 표현할 수 없는 실제 폰트 크기를 억지로 흉내내지
  않는다 — 헤딩 레벨로만 위계를 표현한다.
- "범위 외"·"이 모듈은 무관함"처럼 결론에 직결되는 판단을 project-struct
  문서 서술만 보고 확정하지 않는다 — 문서가 최신 코드와 어긋나 있을 수
  있으므로 관련 코드를 직접 `Read`해서 재확인한다.
