# 요구사항 5W1H 분석

개발/유지보수 업무에서 들어온 요구사항을, 지금 작업 중인 프로젝트의 실제 코드와
함께 확인해서 5W1H(Who/What/When/Where/Why/How) 방식으로 정리한 분석 문서를
만든다. 변경이 간단하지 않으면 Mermaid 다이어그램도 포함한다.

문서 템플릿·변경 유형 목록·다이어그램 판단 기준은
[references/5w1h-template.md](references/5w1h-template.md)에 정리되어 있다 —
작성 전에 반드시 읽는다.

> Jira 등에 올릴 배경 설명 초안만 따로 필요하면, 이 스킬 대신
> `/spec-writer:jira-draft` 서브 스킬을 쓴다.

## 0. 요구사항 파악

사용자가 대화로 설명한 내용을 요구사항으로 삼는다. Jira 티켓 본문 등을
붙여넣었으면 그 내용을 그대로 활용한다. 핵심이 애매하면(범위가 불명확하거나
여러 해석이 가능하면) 코드 조사에 들어가기 전에 `AskUserQuestion`이나 일반
대화로 바로 물어본다 — 이 스킬은 메인 대화에서 동기적으로 실행되므로 중간에
질문해도 흐름이 끊기지 않는다.

## 1. 변경 유형 확인

`references/5w1h-template.md`의 변경 유형 목록을 `AskUserQuestion`으로
제시하고 고르게 한다 (요구사항 설명만으로 이미 명확하면 후보를 좁혀서
"이거 맞나요?" 정도로 확인).

## 2. 코드 조사

1. 현재 프로젝트에서 `Grep`/`Glob`/`Read`로 관련 코드를 찾는다.
2. 관련 파일의 `git log`/`git blame`을 확인해서 왜 지금 이렇게 되어 있는지
   배경을 파악한다 (Why 채우는 데 참고— 커밋 메시지가 배경을 설명해줄 때가
   많다).
3. **외부(다른 프로젝트) 영향 확인** — 사내 시스템은 보통 일부 기능이라도
   서로 엮여있는 경우가 많다는 전제로, 코드 레벨 의존성뿐 아니라 **인프라
   레벨 결합**까지 적극적으로 확인한다 (증거가 나올 때만 반응하는 게
   아니라 기본적으로 점검한다):
   1. **코드 레벨**: 다른 프로젝트/서비스에 대한 의존 흔적을 찾는다 (공유
      라이브러리 참조, 다른 서비스로의 API 호출 URL 등).
   2. **인프라 레벨**: 설정 파일(`application.properties`/`.yml` 등)에서
      DB 접속 정보, 메일 서버, 외부 API 주소, 공유 캐시/메시지 큐 등을
      확인한다. 이 값이 다른 프로젝트와 **같은 호스트/스키마를 가리키면**,
      코드가 직접 연결되어 있지 않아도 실질적으로 결합된 시스템으로 본다
      (예: 같은 DB를 여러 시스템이 나눠 쓰는 경우 — 사내 시스템에서 흔함).
   3. 위에서 흔적이 발견되면, 이 프로젝트의 상위 폴더(형제 프로젝트들이
      모여있는 곳 — 예: 이 프로젝트 경로의 부모 디렉토리)를 살펴서 이름이
      일치하거나 같은 인프라를 가리키는 프로젝트가 있는지 확인하고, 있으면
      그 프로젝트의 관련 코드도 실제로 열어서 확인한다.
   4. 코드/인프라 어디에도 명확한 증거가 없어도, 사용자가 "이 프로젝트도
      봐줘"라고 하면 확인한다.
   5. 증거는 없지만 이름/성격상 관련 있어 보이는 형제 프로젝트가 있으면,
      먼저 "이런 프로젝트도 영향이 있을 수 있는데 확인해볼까요?"라고
      제안한다 — 사용자가 결정하게 한다.
   6. 확인했는데도 아무 연결점을 못 찾았으면 "찾아봤지만 못 찾았다"고
      명시한다("확인 안 함"과 "확인했지만 없음"을 구분한다).

## 3. 5W1H 정리

`references/5w1h-template.md`의 템플릿을 그대로 따라 채운다. **요약은 5W1H를
전부 채운 다음에(내용을 다 알아야 압축할 수 있으니) 맨 마지막에 쓰되, 문서
안에서는 맨 위에 배치한다** — 5줄 이내로 무엇을·왜·어디에 영향·어떻게
바꾸는지가 한눈에 들어오게. 나머지는 특히:

- **Who**: 사람(요청자)이 아니라 **프로젝트(시스템)** 관점으로 쓴다. 영향받는
  다른 시스템이 있는지 여부를 반드시 명시한다 — 이게 핵심 포인트다.
- **When**: 실제 개발 일정이 아니라 **이 코드가 시스템 안에서 언제(어떤
  트리거로) 실행되는지**를 코드 조사로 채운다 — 거의 항상 채울 수 있는
  필수 항목이다. 실제 희망 완료일 등 일정 정보가 파악되면 그건 "일정(있으면)"
  하위 섹션에 별도로 적고, 없으면 그 섹션 자체를 생략한다 ("미정"이라고
  쓰지 않는다).
- **Where**: 2번에서 조사한 내부(모듈/파일/API)와 외부(다른 프로젝트) 영향을
  모두 적는다.
- **Why**: Jira 등에서 배경 텍스트를 이미 받았으면 반영한다. 없으면 대화로
  직접 물어봐서 채운다 — 코드만 보고 배경을 지어내지 않는다.
- **What**: 기능/비기능 요구사항이 섞여 있으면 구분하고, 범위 외(Out of
  Scope)가 있으면 명시한다. **변경 유형이 "버그 수정"이면 범위 외 대신
  재현 절차·기대 결과 vs 실제 결과·환경 정보·심각도를 채운다** — 템플릿의
  버그 전용 항목 참고.
- **우선순위**: 문서 최상단 필드로 독립적으로 채운다 (When에 섞지 않는다).

## 4. 다이어그램

`references/5w1h-template.md`의 포함 기준으로 필요 여부를 판단하고,
필요하면 같은 문서의 종류 선택 표를 참고해 Mermaid 다이어그램을 문서 안에
직접 삽입한다 (별도 이미지 파일 없이 마크다운 코드블록으로). **수정
범위가 넓으면(여러 모듈/시나리오에 걸치면) 넓은 관점(개요) 다이어그램 1개
+ 시나리오별 좁은 관점(상세) 다이어그램으로 나눈다** — 자세한 기준은
템플릿의 "다이어그램 개수 판단" 참고. 범위가 좁으면 좁은 관점 하나로
충분하다.

## 5. 산출물 저장

분석 대상 프로젝트 루트의 `docs/analysis/` 폴더에
`{YYYY-MM-DD}_{요구사항 제목(공백은 하이픈)}.md`로 저장한다. 폴더가 없으면
만든다.

## 6. 완료 보고

저장한 파일 경로를 알려주고, "Jira 배경 초안도 바로 만들어드릴까요?"라고
`AskUserQuestion`으로 물어본다.

- **예**라고 하면, 새 명령을 기다리지 말고 **그 자리에서 이어서**
  `../jira-draft/SKILL.md`(상대경로: `plugins/spec-writer/skills/jira-draft/SKILL.md`)를
  `Read`로 읽고 그 지침을 그대로 따른다. 이때 "1. 원본 확인" 단계에서 파일을
  다시 찾을 필요 없이, 방금 5번에서 저장한 파일을 그대로 원본으로 쓴다.
  (한 번의 `/spec-writer:spec-writer` 호출로 분석 문서 + Jira 초안까지 같이
  나오는 효과 — 별도로 `/spec-writer:jira-draft`를 또 칠 필요가 없다.)
- **아니오**면, 나중에 필요할 때 `/spec-writer:jira-draft`를 실행하면 된다고
  안내하고 끝낸다.
