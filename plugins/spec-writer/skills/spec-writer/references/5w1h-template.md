# 5W1H 분석 문서 템플릿 & 판단 기준

> **참고**: 5W1H(육하원칙)는 사실 개발 전용 표준이 아니라 범용 프레임워크다
> (저널리즘/비즈니스 회의 정리에서 유래). "5W1H가 개발 요구사항 분석의
> 업계 표준"은 아니므로, 실제 IT 요구사항정의서·버그 리포트에서 흔히 쓰는
> 항목([참고](https://www.elancer.co.kr/blog/detail/283))을 5W1H 틀 안에
> 최대한 녹여 넣은 커스텀 구조라는 걸 인지하고 쓴다.

## 변경 유형 (분석 시작 시 AskUserQuestion으로 제시)

- 버그 수정
- 기능 개선
- 신규 기능
- 리팩토링
- 성능 개선
- 기술 부채 해소
- 보안 패치
- 기타 (직접 입력)

## 문서 템플릿

```markdown
# {요구사항 제목}

- 변경 유형: {위 목록 중 선택}
- 우선순위: {긴급/높음/보통/낮음 — 파악 안 되면 "미정"}
- 작성일: {YYYY-MM-DD}

## 요약

{5줄 이내. 무엇을 바꾸는지, 왜, 어디에 영향이 있는지(다른 시스템 포함
여부), 어떻게 할 것인지를 압축. 5W1H를 다 채운 뒤 마지막에 작성한다}

## Who — 프로젝트(시스템)

- 대상 프로젝트(시스템): {이름}
- 영향받는 다른 시스템: {있음/없음 — 있으면 구체적으로. 코드 레벨뿐 아니라
  같은 DB/설정을 공유하는 인프라 레벨 결합도 포함. 이게 핵심 포인트다}

## What — 무엇을

{요구사항 핵심 내용, 변경 유형과 연결해서 요약. 성능/보안/사용성처럼
"어떻게 동작해야 하는가"가 아니라 "어떤 조건을 만족해야 하는가"에 가까운
비기능 요구사항이 섞여 있으면 기능 요구사항과 구분해서 표시한다}

### 범위 외 (Out of Scope)

{이번 변경에 포함되지 않는 것을 명시한다 — 나중에 "이것도 되는 줄
알았다"는 오해를 막는다. 딱히 없으면 이 섹션 생략}

{**버그 수정 유형이면 여기 대신 아래 항목으로 대체한다**:}

### 재현 절차 (버그 수정 유형만)

1. {단계별로 번호를 매겨 재현 조건을 적는다}

### 기대 결과 vs 실제 결과 (버그 수정 유형만)

- 기대: {정상이라면 어떻게 동작해야 하는지}
- 실제: {지금 어떻게 동작하는지/에러가 나는지}

### 환경 정보 (버그 수정 유형만, 파악되면)

{OS/브라우저/서버 환경/버전 등 — 파악 안 되면 "미상"}

### 심각도 (버그 수정 유형만)

{치명적/높음/보통/낮음 — 서비스 전체 장애인지, 일부 기능 불편인지 기준으로 판단}

## When — 실행 시점 (로직 관점)

{이 기능/코드가 시스템 안에서 **언제(어떤 트리거·시나리오에서) 실행되는지**.
코드 조사로 거의 항상 채울 수 있다 (예: "사용자가 마이페이지 저장 버튼을
누를 때", "회원가입 시", "매 페이지 요청마다"). "미정"으로 남기지 말고
실제로 확인해서 쓴다 — 이게 필수 항목이다}

### 일정 (있으면)

{요청 시점/희망 완료일처럼 실제 개발 일정 정보가 파악된 경우에만 쓴다.
우선순위는 최상단에 별도 필드로 이미 있으니 여기서 반복하지 않는다.
**파악 안 되면 "미정"이라고 쓰지 말고 이 하위 섹션 자체를 생략한다** —
매번 "미정"만 나오는 빈 항목을 만들지 않는다}

{영향받는 모듈/클래스/파일/API — 실제로 Read/Grep한 결과 기반}

### 외부(다른 프로젝트)
{조사 절차는 SKILL.md 2번 참고 (코드 레벨 + 인프라 레벨(DB/설정 공유) 둘 다).
발견된 게 있으면 프로젝트명+근거(코드 의존인지 인프라 공유인지 명시),
없으면 "확인했으나 연결점 없음"이라고 쓴다 — "확인 안 함"과 구분한다}

## Why — 왜

{배경/목적. Jira 내용이 있으면 반영, 없으면 사용자와 대화로 채운 내용}

## How — 어떻게

{구현 접근 방식, 변경이 필요한 지점, 기술적 고려사항}
```

## 다이어그램 포함 여부 판단

- **생략**: 단일 파일 로직 수정, 상수/설정값 변경, 단순 버그 픽스
- **포함**: 여러 클래스/모듈 간 상호작용 발생, 신규 API/엔드포인트 추가, DB 스키마 변경, 기존 플로우 변경

## 다이어그램 개수 판단 (넓은 관점 / 좁은 관점)

수정 범위가 넓으면(여러 모듈·여러 시나리오에 걸치면) 다이어그램 하나에
다 욱여넣지 않는다. 대신:

1. **넓은 관점(개요) 다이어그램 1개**: 이번 변경에 관련된 컴포넌트/서비스
   전체가 서로 어떻게 얽히는지 한눈에 보여준다. (예: A 서비스가 B, C
   서비스를 각각 어떤 이유로 호출하게 되는지)
2. **좁은 관점(상세) 다이어그램**: 넓은 관점에서 나온 시나리오 중 핵심
   흐름 각각을 시퀀스 다이어그램으로 자세히 푼다. 시나리오가 여러 개면
   시나리오마다 하나씩 만든다.

각 다이어그램 위에 "(넓은 관점 — 전체 구조)" / "(좁은 관점 — OO 시나리오
상세)"처럼 어떤 관점인지 소제목으로 명시한다. 범위가 좁아서 시나리오가
하나뿐이면 좁은 관점 하나만으로 충분하다 — 억지로 두 개를 만들지 않는다.

## 다이어그램 종류 선택

일반적인 설계 다이어그램 분류(플로우차트/유스케이스/ERD/시퀀스/UML —
[참고](https://www.elancer.co.kr/blog/detail/977))를 기준으로 삼되, 문서마다
다른 스타일을 쓰면 비교하기 어려워지므로 **아래 기준을 항상 동일하게
적용한다** (같은 상황이면 항상 같은 종류를 고른다):

| 변경 성격 | Mermaid 다이어그램 종류 | 비고 |
| --- | --- | --- |
| **기본값** — 컴포넌트/서비스 간 호출과 그 순서가 같이 중요한 경우 (대부분의 요구사항이 여기 해당) | `sequenceDiagram` | 참가자(구조) + 메시지 순서(흐름)를 한 그림에서 같이 보여줄 수 있어 **구조·흐름을 통합해서 봐야 할 때 우선 선택**한다 |
| DB 테이블 관계 자체가 신설/변경되는 경우만 | `erDiagram` | 시퀀스 다이어그램으로는 테이블 간 관계를 표현할 수 없을 때만 예외로 쓴다 |
| 시스템 간 호출보다 사용자 조작 절차·조건 분기 자체가 핵심인 경우만 | `flowchart` | 예: 여러 단계의 승인/조건부 화면 전환처럼 "누가 호출하는지"보다 "어떤 순서로 어떤 조건을 타는지"가 중요할 때 |
| 클래스/모듈의 내부 구조(필드, 메서드, 상속 관계) 자체를 보여줘야 하는 경우만 | `classDiagram` | 호출 순서가 아니라 구조 그 자체가 핵심일 때만 |

기본은 항상 시퀀스 다이어그램이라고 생각하고, 위 표의 예외 조건에 명확히
해당할 때만 다른 종류로 바꾼다. 애매하면 시퀀스 다이어그램을 쓴다 — 여러
종류를 한 문서에 욱여넣지 않는다.
